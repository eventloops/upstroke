# Machine-readable Tactus commit provenance

**Status:** Draft
**Target:** v0.2 (settle before candidate commits and the merge queue make the commit contract broader)
**Filed:** 2026-08-13
**Origin:** owner prompt, 2026-08-13, after self-hosted commits appeared on GitHub under the inherited author name `t`.

---

## Summary

Tactus should identify engine-created commits with structured Git trailers instead of relying on the current `[tactus]` subject prefix or the displayed author name. The recommended new-run shape is:

```text
<task-id>: <task title>

Tactus-Run: <run-id>
Tactus-Task: <task-id>
Tactus-Role: task
Tactus-Commit-Contract: 1
```

The engine should also use an explicit, configurable display identity whose default name is `tactus`, rather than inherit arbitrary repository-local values such as `t`. That identity improves GitHub's presentation; the trailers provide the machine-readable index; the event log remains the authoritative evidence. Tactus does **not** create a Git tag for each commit.

This is provenance, not cryptographic attestation. Anyone who can make a commit can copy an author name or trailer. A trailer says where to look in the local Tactus record; only a matching run log and, later, a signed forge attestation can establish stronger trust.

## Problem

The current v0.1 subject is `[tactus] <task-id>: <title>` (`DESIGN.md` §14 and `engine.rs`). That marker has three jobs mixed into one string:

1. tell a human that the engine created the commit;
2. let tooling find Tactus commits; and
3. help crash recovery recognize the one engine-owned commit that may exist just beyond the event log.

The displayed Git author is no better as the contract. Today it is inherited from repository configuration, which is why self-hosting commits appeared as `t <t@t.local>`. An author can be renamed, overridden, or spoofed; a clone may have different configuration; and author identity alone cannot name the run or task that produced the commit.

Per-commit Git tags would add a second mutable namespace, clutter local and remote refs, require naming and collision rules, interact badly with rebases and garbage collection, and push Tactus toward remote Git ownership that the engine deliberately does not have. The information belongs in the commit object.

## Proposed contract

### 1. Trailers are the durable locator

Every authoritative engine-created task commit carries these exact, single-valued trailers:

- `Tactus-Run`: the recorded run ID.
- `Tactus-Task`: the stable task ID from the frozen plan or append-only task registry.
- `Tactus-Role`: the commit's protocol role. v0.1 uses `task`; v0.2 reserves `candidate` and `integration` so internal candidate objects cannot be mistaken for mainline work.
- `Tactus-Commit-Contract`: the integer contract version used to build and validate the message.

The first contract intentionally does not duplicate model, effort, verdict, cost, or evidence prose. Those facts can contain multiple ordered passes, evolve independently, and already belong in the event log. Copying a summary into Git would create two authorities. `(repository, run, task)` is the join key; `Tactus-Role` says which object is being inspected.

Trailer keys and multiplicity are strict. Unknown future `Tactus-*` keys are preserved but ignored by an older reader; duplicate required keys, invalid run/task identifiers, or an unsupported contract version are not valid Tactus provenance. Parsing should use Git's trailer grammar (`git interpret-trailers --parse` or equivalent behavior), not an ad-hoc split on the final lines.

### 2. Subjects become ordinary human summaries

For a new contract the recommended subject is `<task-id>: <title>`, without `[tactus]`. The task prefix remains useful in ordinary logs; provenance no longer consumes subject space or depends on `git log --grep` matching a decorative token.

The first line remains deterministic because crash recovery must reconstruct it. This proposal does not hand commit-message authorship to the coding agent.

### 3. The display identity is explicit but non-authoritative

For engine-owned commits, Tactus supplies the Git author/committer display identity explicitly instead of mutating or inheriting the user's repository configuration. The recommended default is:

```text
tactus <tactus@tactus.local>
```

Repository configuration may override the display name and email for organizations that require a service identity or the operator's verified address. An override changes presentation only; it never changes whether a commit is recognized as Tactus-created. The engine must apply the frozen run setting only to its own `git commit` invocation and must not rewrite the repository's `user.name` or `user.email`.

GitHub association with a bot account or GitHub App is deliberately separate. A local engine should not impersonate a forge identity, and an unverified display email is not a signature.

### 4. Commit format is frozen per run

`run_started` records the resolved commit contract and display identity. Resumes use that record, not current configuration. Absence in a legacy run means the current `[tactus] <task-id>: <title>` contract and inherited identity, so upgrading Tactus cannot silently change the message expected by an interrupted run.

This may be an additive run-record field if the event-schema rules permit it; otherwise it ships with the next planned schema transition. The important requirement is semantic: old runs keep old messages, new runs cannot change identity or message format halfway through.

## Recovery and verification

The existing crash window remains: Git may contain one reviewed commit after the last recorded event because commit creation and event append cannot be atomic. Trailer adoption must preserve the current fail-closed shape rather than weaken it to “author is tactus” or “message contains a trailer.”

A resume adopts an unrecorded new-contract commit only when all existing structural checks pass and the complete commit message has exactly the frozen subject and trailers expected for that run and task. Parent, branch position, task state, expected message, and tree checks remain required. A copied trailer on an unrelated commit is foreign history and is refused.

The workspace API therefore needs the full commit message, not only `commit_subject`. Tests cover legacy subject recovery and the new full-message path independently. The event appended after adoption records the commit SHA exactly as it does today.

For v0.2, candidate and integration objects must not be double-counted. Candidate commits use `Tactus-Role: candidate`. The commit that advances the authoritative run/mainline history uses `Tactus-Role: integration` and retains the same run/task join keys. If the eventual merge protocol reuses one object rather than creating two, that object receives only the authoritative role. The adopted merge-queue design decides object topology; this proposal only requires the role to describe it truthfully.

## Queries and product claims

Git's pretty format exposes trailers without subject parsing:

```powershell
git log --first-parent --format='%H%x09%(trailers:key=Tactus-Run,valueonly)%x09%(trailers:key=Tactus-Task,valueonly)%x09%(trailers:key=Tactus-Role,valueonly)%x09%s'
```

Consumers should filter the protected branch's reachable authoritative `task`/`integration` commits, not `--all`, which also sees internal candidates and abandoned run branches. The public-run viewer and any “N% built by Tactus” calculation join each trailer-bearing commit to a matching settled run/task record and state exactly what is being counted (commits, changed lines, or tasks).

That wording matters: trailers prove only that Tactus's engine made the commit under its protocol marker. They do not by themselves prove which model authored every line, that a reviewer passed it, or that the commit reached a protected branch. Those claims require the event record and forge state.

## Compatibility and migration

- Existing commits are never rewritten. Their SHAs have already been reviewed and may be referenced by run logs and pull requests.
- Legacy `[tactus]` subjects remain recognized as contract 0. New commits use trailers only after their run freezes contract 1.
- During a short compatibility period, status/reporting tools may recognize both forms. The engine should not emit both indefinitely: duplicating the marker in subject and trailers defeats the cleanup and invites consumers to keep parsing the subject.
- Documentation that currently recommends `git log --grep='[tactus]'` moves to trailer-aware queries once contract 1 ships.
- The local `tactus` author-name workaround used during self-hosting can remain until explicit per-invocation identity lands; it is operational configuration, not the protocol.

## Tests required

1. A fresh contract-1 task commit has the exact deterministic subject and four required trailers, and no `[tactus]` prefix.
2. Values containing newlines or trailer-like text are rejected or normalized before commit construction; task titles cannot inject trailers.
3. Duplicate, missing, malformed, and unsupported trailers fail provenance parsing.
4. Custom display identity changes author/committer presentation but not provenance detection; unrelated user commits retain the user's Git configuration.
5. A legacy run resumes with contract 0 and can adopt its exact `[tactus]` crash-window commit.
6. A contract-1 run adopts only the exact expected full message and refuses a matching author with wrong trailers, copied trailers with the wrong parent/tree/task, or the right trailers in the wrong protocol role.
7. Live fold and replay preserve the frozen contract and display identity; changing repository configuration mid-run has no effect.
8. Candidate and integration queries cannot count one successful task twice.
9. Windows, macOS, and Linux produce byte-identical message bodies for the same frozen inputs.

## Non-goals

- No Git tag per task or run.
- No remote push, tag publication, GitHub API call, or forge ownership in the engine.
- No claim that author names or trailers are tamper-proof.
- No commit signing requirement; signed commits and the v0.3+ forge-attestation design solve different trust problems.
- No history rewrite to rename existing `t` commits.

## Open questions for council

1. Is `tactus <tactus@tactus.local>` the right portable default, or should the default retain the operator's email while fixing only the name?
2. Does v0.2 need both `candidate` and `integration` trailer roles, or can its final object topology guarantee one authoritative role per task?
3. Should a stable internal task key be an additional trailer once the ordered task registry lands, or is run ID plus unique task ID sufficient?
4. Should `Tactus-Commit-Contract` begin at `1`, treating the legacy subject as implicit contract `0`, or use a more descriptive value such as `trailers-v1`?

## Rejected alternatives

- **Use only author name `tactus`.** Pleasant in GitHub, but clone-local, configurable, and unable to identify a run or task. Keep it as display identity, not protocol.
- **Keep only `[tactus]` in the subject.** Human-readable but structurally weak, consumes subject space, and cannot name the run or distinguish candidate from integration objects.
- **Create a Git tag for every Tactus commit.** Ref clutter, collision and publication policy, mutable provenance, and an unnecessary remote-facing namespace.
- **Put the complete review record in trailers.** Duplicates an append-only authority into a size-constrained message and becomes stale as evidence schemas evolve.
- **Sign every task commit immediately.** Potentially useful organization policy, but key custody and signing availability are orthogonal to local run/task indexing and should not block the smaller provenance contract.
