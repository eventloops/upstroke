# Machine-readable Tactus commit provenance

**Status:** Draft
**Target:** v0.2 (settle before candidate commits and the merge queue make the commit contract broader)
**Filed:** 2026-08-13
**Origin:** owner prompt, 2026-08-13, after self-hosted commits appeared on GitHub under the inherited author name `t`.
**Revision:** 2026-08-13 — retained `[tactus]` as the human-visible subject marker; added an explicit initial-work → fix lineage with namespaced annotated revision tags.

---

## Summary

Tactus should identify engine-created commits with structured Git trailers instead of relying **only** on the current `[tactus]` subject marker or the displayed author name. The marker remains as the immediate human signal; the trailers make it machine-readable. The recommended new-run shape is:

```text
[tactus] <task-id>: <task title>

Tactus-Run: <run-id>
Tactus-Task: <task-id>
Tactus-Work: <root-task-key>
Tactus-Revision: 0
Tactus-Change-Kind: initial
Tactus-Role: task
Tactus-Commit-Contract: 1
```

The engine should also use an explicit, configurable display identity whose default name is `tactus`, rather than inherit arbitrary repository-local values such as `t`. That identity improves GitHub's presentation; `[tactus]` keeps commits visually obvious; the trailers provide the machine-readable index; optional namespaced annotated tags provide direct aliases to selected authoritative commits; the event log remains the authoritative evidence.

This proposal covers accepted commit lineage. Unreviewed A/B/C states inside one long implementation belong to the sibling [implementation-checkpoint proposal](2026-08-13-v0.2-implementation-checkpoints.md), which preserves private rewind points without presenting them as accepted revisions.

This is provenance, not cryptographic attestation. Anyone who can make a commit can copy an author name, `[tactus]` marker, or trailer. A trailer says where to look in the local Tactus record; only a matching run log and, later, a signed forge attestation can establish stronger trust.

## Problem

The current v0.1 subject is `[tactus] <task-id>: <title>` (`DESIGN.md` §14 and `engine.rs`). That marker currently has three jobs mixed into one string:

1. tell a human that the engine created the commit;
2. let tooling find Tactus commits; and
3. help crash recovery recognize the one engine-owned commit that may exist just beyond the event log.

The displayed Git author is no better as the contract. Today it is inherited from repository configuration, which is why self-hosting commits appeared as `t <t@t.local>`. An author can be renamed, overridden, or spoofed; a clone may have different configuration; and author identity alone cannot name the run or task that produced the commit.

The proposal separates those jobs without discarding the useful visual label: `[tactus]` keeps job 1, while trailers take jobs 2 and 3. Git tag refs can then serve their narrower strength: a direct, human-named anchor to an important authoritative commit. They are a poor primary provenance record because they live outside the commit, may not be fetched or pushed, can be moved or deleted unless protected, and do not follow a cherry-pick or rewritten integration commit. The structured identity therefore belongs in the commit object even when a tag points to it.

## Proposed contract

### 1. Trailers are the durable locator

Every authoritative engine-created task commit carries these exact, single-valued trailers:

- `Tactus-Run`: the recorded run ID.
- `Tactus-Task`: the stable task ID from the frozen plan or append-only task registry.
- `Tactus-Work`: the engine-issued root task key shared by the initial work and every later repair in that logical lineage.
- `Tactus-Revision`: zero for the first accepted commit, then a contiguous integer for each later accepted repair.
- `Tactus-Change-Kind`: `initial`, `review_fix`, `merge_fix`, or `follow_up`; this describes why the revision exists rather than asking consumers to infer it from prose.
- `Tactus-Role`: the commit's protocol role. v0.1 uses `task`; v0.2 reserves `candidate` and `integration` so internal candidate objects cannot be mistaken for mainline work.
- `Tactus-Commit-Contract`: the integer contract version used to build and validate the message.

Every revision after zero also carries `Tactus-Previous`, the full SHA of the immediately preceding accepted revision in the same work lineage. The event/task registry authorizes the lineage and next number; the implementer cannot choose them. A repair task keeps its own `Tactus-Task` identity while joining the original work through `Tactus-Work`.

The first contract intentionally does not duplicate model, effort, verdict, cost, or evidence prose. Those facts can contain multiple ordered passes, evolve independently, and already belong in the event log. Copying a summary into Git would create two authorities. `(repository, run, task)` locates the producing task; `(repository, run, work, revision)` locates its place in the logical change series; `Tactus-Role` says which object is being inspected.

Trailer keys and multiplicity are strict. Unknown future `Tactus-*` keys are preserved but ignored by an older reader; duplicate required keys, invalid run/task identifiers, or an unsupported contract version are not valid Tactus provenance. Parsing should use Git's trailer grammar (`git interpret-trailers --parse` or equivalent behavior), not an ad-hoc split on the final lines.

### 2. The subject marker remains the human signal

For a new contract the recommended subject remains `[tactus] <task-id>: <title>`. GitHub and an ordinary one-line log therefore remain scannable, and `git log --grep='^\[tactus\]'` remains a useful convenience filter. The marker is explicitly a display label, not proof and not the interface on which protocol tooling relies.

The first line remains deterministic because crash recovery must reconstruct it. This proposal does not hand commit-message authorship to the coding agent.

### 3. The display identity is explicit but non-authoritative

For engine-owned commits, Tactus supplies the Git author/committer display identity explicitly instead of mutating or inheriting the user's repository configuration. The recommended default is:

```text
tactus <tactus@tactus.local>
```

Repository configuration may override the display name and email for organizations that require a service identity or the operator's verified address. An override changes presentation only; it never changes whether a commit is recognized as Tactus-created. The engine must apply the frozen run setting only to its own `git commit` invocation and must not rewrite the repository's `user.name` or `user.email`.

GitHub association with a bot account or GitHub App is deliberately separate. A local engine should not impersonate a forge identity, and an unverified display email is not a signature.

### 4. Commit format is frozen per run

`run_started` records the resolved commit contract and display identity. Resumes use that record, not current configuration. Absence in a legacy run means the current `[tactus] <task-id>: <title>` contract and inherited identity, so upgrading Tactus cannot silently change the message expected by an interrupted run.

This may be an additive run-record field if the event-schema rules permit it; otherwise it ships with the next planned schema transition. The important requirement is semantic: old runs keep old messages, new runs cannot change identity or message format halfway through.

### 5. Optional annotated tags are secondary anchors

Repositories may opt into namespaced annotated tags for every **accepted revision** worth addressing directly:

```text
tactus/run/<run-id>
tactus/run/<run-id>/work/<work-key>/revision/0
tactus/run/<run-id>/work/<work-key>/revision/1
tactus/run/<run-id>/work/<work-key>/revision/2
```

The run tag is created only after the run settles and points to its final authoritative head. Revision tags use an engine-issued, Git-ref-safe work key rather than interpolating an arbitrary plan ID. Revision 0's annotation is `Initial work`; later repair annotations are `Fix 1`, `Fix 2`, and so on (an explicit follow-up uses `Follow-up N`), plus the machine change kind and producing task. This yields the common direct chain the owner asked for:

```text
Initial work → Fix 1 → Fix 2
```

Each tag points only to the corresponding accepted authoritative `task`/`integration` commit—never a failed attempt or disposable candidate. The numeric path is canonical and stable; the friendly annotation can evolve without becoming an API. Consumers accept a tag as a Tactus anchor only when its target's run/work/revision trailers, predecessor link, and event record agree.

This distinction matches the current verification protocol. Implementation attempts and review-directed edits before the first PASS are cumulative worktree states and eventually become **one** revision-0 commit; there is no honest “initial commit” to tag before acceptance. A later review finding, merge rejection, or explicit follow-up that settles as a separate authoritative commit becomes revision 1, then revision 2. Preserving every rejected intermediate tree would be a different audit-artifact proposal, not commit provenance.

Tags are opt-in because a busy repository may not want one long-lived ref per accepted revision, while an audit-oriented repository may value direct lookup, visual lineage, and keeping those objects reachable. Tactus creates them locally under its Git ownership boundary. Publishing them to a remote is a separate explicit notifier/forge action; the core engine never pushes them implicitly. A repository that publishes the namespace should protect it from update and deletion, and may sign annotated tags under an independently designed key policy.

Neither recovery nor replay depends on a tag being present. Missing tags cannot make an otherwise valid run unreadable, and a tag cannot make an invalid commit adoptable.

## Recovery and verification

The existing crash window remains: Git may contain one reviewed commit after the last recorded event because commit creation and event append cannot be atomic. Trailer adoption must preserve the current fail-closed shape rather than weaken it to “author is tactus” or “message contains a trailer.”

A resume adopts an unrecorded new-contract commit only when all existing structural checks pass and the complete commit message has exactly the frozen subject and trailers expected for that run and task. Parent, branch position, task state, expected message, and tree checks remain required. A copied trailer on an unrelated commit is foreign history and is refused.

The workspace API therefore needs the full commit message, not only `commit_subject`. Tests cover legacy subject recovery and the new full-message path independently. The event appended after adoption records the commit SHA exactly as it does today.

For v0.2, candidate and integration objects must not be double-counted. Candidate commits use `Tactus-Role: candidate`. The commit that advances the authoritative run/mainline history uses `Tactus-Role: integration` and retains the same run/task/work/revision identity. If the eventual merge protocol reuses one object rather than creating two, that object receives only the authoritative role. A public revision tag is created only after integration and points directly at the authoritative object; candidate refs remain private protocol state and are never retagged or published as accepted revisions. The adopted merge-queue design decides object topology; this proposal only requires the role to describe it truthfully.

## Queries and product claims

Git's pretty format exposes trailers without subject parsing:

```powershell
git log origin/master --format='%H%x09%(trailers:key=Tactus-Run,valueonly)%x09%(trailers:key=Tactus-Work,valueonly)%x09%(trailers:key=Tactus-Revision,valueonly)%x09%(trailers:key=Tactus-Change-Kind,valueonly)%x09%s'
```

Here `origin/master` stands for the repository's protected target. Consumers search that target's complete reachable history—not `--first-parent`, which would hide commits on merged topic branches, and not `--all`, which also sees internal candidates and abandoned run branches. The public-run viewer and any “N% built by Tactus” calculation join each trailer-bearing commit to a matching settled run/task record and state exactly what is being counted (commits, changed lines, or tasks).

When optional tags are enabled, direct lookup and ordered listing become trivial:

```powershell
git tag --list 'tactus/run/*/work/*/revision/*' --sort=version:refname
git show tactus/run/<run-id>/work/<work-key>/revision/1
```

Aggregate queries still use trailers and reachability so the answer does not depend on which optional aliases happened to be published.

That wording matters: trailers prove only that Tactus's engine made the commit under its protocol marker. They do not by themselves prove which model authored every line, that a reviewer passed it, or that the commit reached a protected branch. Those claims require the event record and forge state.

## Compatibility and migration

- Existing commits are never rewritten. Their SHAs have already been reviewed and may be referenced by run logs and pull requests.
- Legacy `[tactus]` subjects without trailers remain recognized as contract 0. New contract-1 commits retain the marker and add trailers.
- Status/reporting and provenance tooling recognize both contracts, but protocol decisions use trailers whenever contract 1 is present. The subject remains for humans and compatibility, never as a substitute for structured parsing.
- Documentation may keep `git log --grep='^\[tactus\]'` as a quick visual filter while using trailer-aware queries for run/task joins and product metrics.
- The local `tactus` author-name workaround used during self-hosting can remain until explicit per-invocation identity lands; it is operational configuration, not the protocol.

## Tests required

1. A fresh contract-1 task commit has the exact deterministic `[tactus]` subject, revision 0, change kind `initial`, and every required trailer.
2. Values containing newlines or trailer-like text are rejected or normalized before commit construction; task titles cannot inject trailers.
3. Duplicate, missing, malformed, and unsupported trailers fail provenance parsing.
4. Custom display identity changes author/committer presentation but not provenance detection; unrelated user commits retain the user's Git configuration.
5. A legacy run resumes with contract 0 and can adopt its exact `[tactus]` crash-window commit.
6. A contract-1 run adopts only the exact expected full message and refuses a matching author with wrong trailers, copied trailers with the wrong parent/tree/task, or the right trailers in the wrong protocol role.
7. Live fold and replay preserve the frozen contract and display identity; changing repository configuration mid-run has no effect.
8. Candidate and integration queries cannot count one successful task twice.
9. Windows, macOS, and Linux produce byte-identical message bodies for the same frozen inputs.
10. A repair retains its own task identity, shares the root work key, increments the revision contiguously, uses the right change kind, and points `Tactus-Previous` at the preceding accepted revision.
11. When tags are enabled, revision 0 is annotated `Initial work`, later repairs are ordered `Fix N` (with explicit follow-ups labelled accordingly), only settled authoritative commits receive them, mismatched tags fail validation, and disabled tagging creates none.

## Non-goals

- No mandatory tag per attempt or candidate. Optional run/revision tags are secondary indexes only; the `[tactus]` commit-message marker remains.
- No remote push, tag publication, GitHub API call, or forge ownership in the engine.
- No claim that author names or trailers are tamper-proof.
- No commit signing requirement; signed commits and the v0.3+ forge-attestation design solve different trust problems.
- No history rewrite to rename existing `t` commits.

## Open questions for council

1. Is `tactus <tactus@tactus.local>` the right portable default, or should the default retain the operator's email while fixing only the name?
2. Does v0.2 need both `candidate` and `integration` trailer roles, or can its final object topology guarantee one authoritative role per task?
3. Should a stable internal task key be an additional trailer once the ordered task registry lands, or is run ID plus unique task ID sufficient?
4. Should `Tactus-Commit-Contract` begin at `1`, treating the legacy subject as implicit contract `0`, or use a more descriptive value such as `trailers-v1`?
5. Should the default create only the final run tag, or the full accepted-revision chain? The owner preference for self-hosting repositories is the full chain; library defaults may reasonably remain off until remote publication policy exists.

## Rejected alternatives

- **Use only author name `tactus`.** Pleasant in GitHub, but clone-local, configurable, and unable to identify a run or task. Keep it as display identity, not protocol.
- **Keep only `[tactus]` in the subject.** Human-readable but structurally weak and unable to name the run or distinguish candidate from integration objects. Keep it as a label, not the whole contract.
- **Tag every attempt and internal candidate as `Initial work` / `Fix N`.** Current pre-PASS fixes are not commits, and retaining rejected trees would make “tagged” look synonymous with “accepted.” Revision labels are reserved for separately settled authoritative commits; attempt history remains in the event log.
- **Put the complete review record in trailers.** Duplicates an append-only authority into a size-constrained message and becomes stale as evidence schemas evolve.
- **Sign every task commit immediately.** Potentially useful organization policy, but key custody and signing availability are orthogonal to local run/task indexing and should not block the smaller provenance contract.
