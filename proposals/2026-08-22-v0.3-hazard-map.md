# Repository hazard map: path-indexed design defects, fed back into Phase 1

**Status:** Draft
**Target:** v0.3 (the "design-defect feedback loop surfacing into the designer prompt" item — this is its data model)
**Filed:** 2026-08-22
**Origin:** owner prompt, 2026-08-22 ("a documentation of the pain points within the repository, not just within the individual story"); designed against DESIGN.md §5/§8/§23, the v16 packet's `path_policy`, and `reviews/FINDINGS.md` in a Fable 5 session (Anthropic seat).
**Revised:** 2026-08-22, after round 1 of the filing PR's frontier review (gpt-5.6-sol, max): hints are now projected under `PathPolicy v1` before overlap (`HAZARD-HINT-GLOB`); areas are byte-safe and carry a repo-wide variant (`HAZARD-GITPATH-FALLBACK`); the committed rendering is the carrier, not optional (`HAZARD-SHARED-CARRIER`); matching, merging, ordering and identity rules are stated (`HAZARD-DEDUPE-RULE`); unclassified defects enter as provisional and invariant 6 says so (`HAZARD-UNCLASSIFIED-CONTRACT`).

---

## Summary

Every question that reaches a human at runtime is, by the design's own definition, a design-phase
defect (§5). Today it is logged as one — `design_defect`, with question and answer — in the event
log of the run that suffered it, and it never reaches the next designer. The reviewer side has
repository-wide memory: `reviews/FINDINGS.md` is "an input to every review," and the review gate
hands every reviewer `DESIGN.md` and the ledger. The designer side has none. A story planned a
year after the last work in an area is planned by a model with no record that the area bit
someone.

**Design verdict: a derived, path-indexed projection of design defects and path-bound review
findings — the hazard map — consumed at Phase 1 by overlap with the story's `path_hints`, where
each overlapping live hazard becomes a mandatory question-exhaustion item the plan cannot freeze
without addressing.** No new event types; one additive field on `question_answered`; one
read-only local projection command; one Phase-1 injection. The governing invariant: **the map
generates questions, never answers.** A hazard can force the designer to resolve something; it
can never resolve it for them, because the same area legitimately gets different answers in
different stories.

The idea is narrower than "the AI's representation of the codebase." The data that exists is a
(path × time) matrix of recorded pain with counts and recency; its honest picture is a treemap
over the file tree, and its honest use is a checklist.

## What exists today (measured against source and this week's evidence)

- **The data is already recorded, in two halves that are never joined.** `design_defect` is an
  event with the question and eventual answer (§8, event list at DESIGN.md:404). Every task
  records its predicted paths at dispatch and its *actual* changed paths at candidate time —
  `git diff-tree -r -z -M --name-status`, both rename endpoints, byte-safe (packet
  `decisions.admission_and_leases.path_policy.actual`). Defect × area is a join over one run's
  own log; nothing performs it.
- **"Area" already has a definition.** The lease-overlap predicate — component-wise equal,
  ancestor, or descendant after forward-slash normalisation, case-folded when the repository
  is — is frozen per run as `PathPolicy v1`. This proposal reuses it unchanged rather than
  inventing geometry.
- **The reviewer's memory exists and is path-bound.** `FINDINGS.md` rows bind to
  `<reviewed SHA> / <path>:<line>`, carry recurrence counts, and grant a "recurrence class" only
  at two occurrences. Its authority rule (the implementer holds the disposition) is the template
  for who may settle a hazard.
- **The carrier into prompts exists and is per story.** The conventions brief is "injected into
  every downstream prompt" (§5); the runtime pre-filter consults only *the story's* decisions
  record — correctly, since answers are story-scoped.
- **The roadmap names the slot and leaves it empty.** "No cross-run learning in v0.x"
  (DESIGN.md:50) parks anything statistical; v0.3 direction lists "the design-defect feedback
  loop surfacing into the designer prompt" (DESIGN.md:616) with no data model. The
  review-finding-telemetry proposal (2026-08-13) adds a `path` to every structured finding — the
  review-side feed this map would consume; the two compose.
- **Four hazards of building this, each measured on this repository this month:**
  1. *The reading trap.* The v16 packet carries fourteen generations of resolved rationale
     inline, and every reviewer now needs a standing warning that superseded reasoning reads
     exactly like specification. A map that feeds raw accumulated defects forward recreates it.
  2. *Non-determinism.* Two runs of an identical configuration on one task produced two
     different failure modes — a review rejection and a parked question (DESIGN.md:659). One
     parked question is weak evidence about the code.
  3. *Paths move.* `DRIFT-RENAME-ENDPOINT` on PR #22: a rename onto an exempt path hid its source
     under `--name-only`. A map keyed by path alone goes stale on every refactor, silently.
  4. *Survivorship.* Pain is recorded where work happened. The areas no run has exercised are
     not safe; they are unknown.

## The change

### 1. Classify defects when they are answered

`question_answered` gains one optional, additive field (the `#[serde(default)]` precedent; no
schema bump):

```
kind: code_fact | product_decision | plan_wording      // absent → unclassified
```

`code_fact` enters the map: the answer revealed something true of the code that the plan did
not know. `product_decision` is the user-owned call §5 says models never resolve; it stays in
the story's decisions record and never enters the map. `plan_wording` is a defect in the task
text and never enters either. An `unclassified` defect — every defect recorded before this
field existed is one — enters as **provisional**: it surfaces exactly as a `code_fact` hazard
does, flagged as unclassified and weighted below classified entries, because the conservative
reading of "the map asks, never answers" is that an unknown kind must still be asked about. A
provisional entry becomes `code_fact` (or leaves the map) when a human classifies it. The
human answering tags it; a model-inferred default is an open question for the council (below).

Defects raised from `fix` tasks are weighted above those from `implement` tasks. A bug is, by
definition, where the code's behaviour diverged from everyone's model of it; a fix task's
question names the exact place the model was wrong, and that is the knowledge least likely to be
re-derived a year later.

### 2. The projection: `tactus hazards`

A local, read-only, versioned projection in the `export-decisions` mould (§9 posture: no
network; refuses a live run). Inputs: every settled run's event log under the repository's run
directories, and `reviews/FINDINGS.md` rows. Output, `hazards.json`:

```
hazard:
  id            stable: sha256(source, canonical first area, first question)   (§2a)
  source        design_defect | review_finding
  kind          code_fact | provisional             (review findings: their category)
  task_type     implement | fix | design | …        (weighting input)
  areas         [ area ]                            (keys; resolved at read time, §4)
  question      the question as asked, or the finding summary
  settled       { answer, by, at, run_id }          exactly one, live
  history       [ { answer, by, at, run_id } ]      append-only, visibly history
  occurrences   n                                    distinct runs that raised it in this area
  first_seen / last_seen
  origin        { run_id, task_key, external_ref? }  traces to the story

area:
  { path: <GitPath, byte-safe>, observed_sha }      a concrete path, or
  repo_wide                                          overlaps everything
```

Areas carry the packet's own path type. `path_policy.actual` records changed paths as
NUL-delimited bytes, `GitPath` byte-safe, and classifies an undecodable path as repo-wide; the
map does the same. A path is stored as bytes (escaped in JSON; never lossily decoded), and a
hazard whose actual path was undecodable, unparsable, or absent gets the `repo_wide` area —
which overlaps every later hint, so the hazard surfaces everywhere rather than nowhere. A
rejected or omitted path is not a representable state.

Aggregation is by area under the frozen overlap predicate: per prefix, hazard count, recurrence,
most recent occurrence. The map also emits the **unknown set**: paths present at `HEAD` that no
recorded run's actual-path set has ever touched, rendered distinctly from "no hazards."

### 2a. Matching, merging, ordering, identity

The overlap predicate (equal, ancestor, or descendant) is not transitive: `src/api` overlaps
both `src/api/client.rs` and `src/api/server.rs`, which do not overlap each other. The rules:

- **A hazard's identity is its first canonical area plus its first question, never a merged
  area.** `id = sha256(source, canonical(first area), first question)`; canonical means
  forward-slash normalised, case-folded when the repository's policy is, components joined
  with a single `/`, `repo_wide` spelled literally. Identity never changes after creation.
- **No bridge merging.** A new occurrence whose area overlaps several existing hazards attaches
  as an occurrence to *each* of them; it does not fuse them into one, and it does not widen any
  hazard's stored areas. Hazards only ever gain areas from their own later occurrences.
- **Projection ordering is deterministic:** by `first_seen`, then `id`. Two projections of the
  same logs are byte-identical.
- **A repo-wide area overlaps every hint**, so a repo-wide hazard is always surfaced and is
  always a flag to narrow, never silently absorbed into another hazard.

### 3. Live versus history, from the first entry

Each hazard carries exactly one `settled` answer marked live. A later run raising the same
question in an overlapping area appends to that hazard: `occurrences` increments, and the new
answer either confirms (history gains the confirmation) or supersedes (the old `settled` moves to
history with its date; the new one becomes live). The designer receives **only** live settled
answers and counts; history is available on demand and never in the prompt by default. This is
the packet's live/history split adopted deliberately instead of learned painfully.

### 4. Keys that survive refactors

A concrete area is `(path, observed_sha)`, never a bare path. At read time each key is resolved
to the current path by following renames from `observed_sha` to `HEAD`; an unresolvable key
renders as `moved/unknown`, never silently dropped — the exact failure `--no-renames` closed in
the review gate, applied in the other direction. A `repo_wide` area needs no resolution and
overlaps every hint at every `HEAD`.

### 5. Phase 1 consumption: overlap becomes obligation

At design time the engine **projects** the story's hints exactly as `PathPolicy v1` does for a
dispatch lease — the literal prefix before the first glob metacharacter after forward-slash
normalisation; an unsafe or unparsable hint, or no hints at all, projects to repo-wide — and
then computes `overlap(projected_hints, map.areas)` with the lease predicate. The projection
is not optional: passing a raw `src/api/**` to component-wise overlap diverges at the `**`
component and would miss a live hazard at `src/api/client.rs`; projected to `src/api` it
overlaps, as it must. Each overlapping **live** hazard becomes a mandatory question-exhaustion
item. The decisions record gains, per such hazard:

```
hazard_ack: { hazard_id, disposition: accounted | not_applicable | needs_user, note }
```

`tactus validate` refuses to freeze a plan that overlaps a live hazard without an `ack`.
`needs_user` raises the question to the human *at design time* — which is the entire point:
the question that would have parked a worker at 3 a.m. is asked while the human is present and
cheap. Absent, unsafe, or unparsable hints project to repo-wide, exactly as for leases, so every
live hazard surfaces — conservative, and a standing incentive to write precise hints.

Wording is tied to recurrence: a single occurrence renders as a **flag** ("the last change here
tripped on X — check it"); two or more as a **class** ("known hazard: X"), matching the ledger's
own threshold. Nothing decays. A year-old single flag is precisely the case the map exists for;
recency is shown, never used to hide.

### 6. Where it lives: the repository is the carrier

Run event logs are local to one checkout — a second seat, a fresh clone, or the build box
after a rebuild has none of them. So the committed rendering is **not optional; it is the
input Phase 1 reads.** `tactus hazards` folds every settled local run plus the current
`reviews/FINDINGS.md` into `reviews/hazards.json` (canonical, generated, byte-stable under §2a's
ordering) and `reviews/HAZARDS.md` (the human view, one section per area), and a run that
produced new hazards commits that delta in the same pull request that carries its ledger. The
designer reads `reviews/hazards.json` at `HEAD`, exactly as every reviewer already reads
`FINDINGS.md` at `HEAD`: the repository carries the memory, so whoever clones it inherits it.

The event logs remain the evidence behind each entry and the ledger rows the evidence behind
each review-sourced one; the committed file is a projection of both that a reviewer can diff.
Nobody maintains the map by hand; a slice pull request carries its delta because the process
already requires the records the delta is folded from. A clone whose local logs are older than
the committed file never regresses it: the projection is a union keyed by identity, and an
entry known to the committed file but absent locally is kept, not dropped.

### 7. Visualisation

A treemap over the file tree: size by churn or lines, colour by hazard count weighted toward
recency and `fix` origin, grey for the unknown set. It belongs in the design pane and the public
run viewer (proposal 2026-08-13). A third spatial dimension is rejected below; the data has none.

## Invariants

1. **The map generates questions, never answers.** It can add a mandatory item to Phase 1; it
   cannot satisfy one.
2. **Absence renders as unknown, never as safe.**
3. **One live settled answer per hazard; history is append-only and visibly history.**
4. **Keys are byte-safe `(path, observed_sha)` areas or `repo_wide`, resolved at read time;
   unresolvable keys are shown as moved, undecodable paths become `repo_wide`, and nothing is
   ever dropped.** The packet's `path_policy.actual` fallback, applied unchanged.
5. **One occurrence is a flag; two are a class; the wording differs.** Same threshold as
   `FINDINGS.md`.
6. **Only `code_fact` defects, `provisional` (unclassified) defects, and path-bound review
   findings enter the map.** `product_decision` and `plan_wording` never do; a provisional entry
   surfaces like a `code_fact` one until a human classifies it.
7. **Read-only, local, no network; refuses a live run.** The §9 posture and the
   `export-decisions` precedent.
8. **Repository is the boundary, and the repository is the carrier.** Phase 1 reads the
   committed `reviews/hazards.json` at `HEAD`; cross-repository aggregation is cross-run
   learning, parked.
9. **Hints are projected before overlap, exactly as leases are.** Raw globs never reach the
   predicate; unsafe, unparsable, or absent hints are repo-wide.
10. **No bridge merging; identity is fixed at creation; projection order is deterministic.**

## Measured vs assumed

Measured: the events and actual paths exist (source and packet, cited above); `FINDINGS.md`
binds rows to paths and thresholds recurrence at two; the reading trap, the non-determinism, the
rename hole, and the reviewer/designer memory asymmetry are all recorded on this repository in
August 2026. Assumed, and named as the hypothesis this proposal stands or falls on: **that
hazards overlapping a story's `path_hints` predict where its runtime questions would have
occurred.** It is cheap to test before building anything beyond the projection — see acceptance.

## Acceptance — how we would know

- **Replay over existing history, first.** Build the map from runs PR0b–PR(n−1) and ask, for
  each `design_defect` in run PR(n), whether its area carried a prior live hazard. The hit rate
  over this repository's own self-hosting history is the calibration test, in the spirit of
  §23.2's "ask a frontier model to predict against runs whose outcome is already known." A low
  hit rate parks the Phase-1 injection and keeps only the projection.
- **The §23 refinement metric, per area.** Defects per story in mapped areas should fall over
  time relative to unmapped areas.
- **Cost.** Zero model calls to build; Phase 1 gains N mandatory questions where N is the number
  of overlapping live hazards, bounded by the hints given.
- **Legacy logs.** Every `design_defect` recorded before the `kind` field existed is
  unclassified; the acceptance case is that each one surfaces as a provisional hazard under a
  repo-wide or projected hint, and none is silently excluded.
- **Projection fixtures.** A glob hint against a concrete area (`src/api/**` must overlap
  `src/api/client.rs`); an undecodable actual path yielding a `repo_wide` area that overlaps an
  unrelated hint; a fresh clone with no local logs reading the committed file and surfacing the
  same hazards as the seat that produced them; two projections of identical inputs being
  byte-identical.

## Rejected options

- **Feed the raw defect log into the designer prompt.** The reading trap, plus unbounded
  context. The packet is the existence proof of what that produces.
- **A learned risk model over areas.** The routing-dataset argument applies: single-digit samples
  per cell, quarterly churn. And unnecessary — one recorded hazard is actionable at n = 1 when it
  is framed as a question rather than a probability.
- **A third spatial dimension.** The data is path × time with weights; a treemap says all of it.
- **A hand-maintained hazard wiki.** Rots. `FINDINGS.md` works because it is an input to the
  process with a disposition rule, not prose someone is supposed to remember to update.
- **A repository-wide decisions record consulted by the runtime pre-filter.** Answers are
  story-scoped; reusing one story's answer in another is how the wrong decision gets inherited
  silently. The map asks; the story's record answers.
- **Cross-repository maps.** Cross-run learning is parked; the repository is the boundary.

## Open questions for the council

1. Classification at answer time: human-tagged `kind`, or a model-inferred default the human can
   correct?
2. One map with two sources, or two layers (design defects; review findings) with separate
   weighting?
3. *(Resolved in revision: the committed `reviews/hazards.json` is the carrier and the slice
   pull request commits its delta — see §6. Whether the body must additionally summarise the
   delta, the way it carries a ledger, remains open.)*
4. Is "nothing decays" right, or should recency change wording as well as ordering?
5. How does a `hazard_ack` of `not_applicable` get audited when the story later parks on that
   exact question? (Proposal: it becomes a second occurrence with the ack recorded as history —
   the map remembers being overruled.)
