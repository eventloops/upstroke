# Pull-request rationale and acceptance traceability

## Summary

Every pull request should explain not only what changed, but why each meaningful
change exists and which acceptance criterion it satisfies. The description is
review evidence: reviewers judge its accuracy and completeness alongside the
exact code, tests, and design records.

This is not a demand for a longer changelog. It is a compact trace from intent
to implementation to proof, readable by maintainers and structured enough for
Upstroke to validate.

## Required PR evidence

A Upstroke-managed PR body contains these stable sections:

1. **Intent and why now** — the problem, user outcome, and reason for the chosen
   timing.
2. **Changes and rationale** — each material change paired with why that shape
   was chosen; mechanical edits may be grouped.
3. **Acceptance trace** — every frozen acceptance criterion mapped to the code,
   test, command, or artifact that proves it.
4. **Risks and non-goals** — affected invariants, known limitations, and work
   deliberately excluded.
5. **Verification** — exact gates and review evidence, distinguishing current
   exact-head results from planned or historical results.
6. **Deferred findings** — stable links into the defect backlog, with an
   explicit reason none is silently omitted.
7. **Rollback or recovery** — the safest way to undo or contain the change,
   including any irreversible step.

The acceptance trace is a small table:

| Acceptance criterion | Change/evidence | Result |
|---|---|---|
| stable criterion ID and text | paths, test names, run/check links | pass, deferred, or not applicable with reason |

## Review contract

The reviewer receives the canonical PR evidence with the plan, decisions,
repository conventions, exact candidate diff, and resulting tree. It checks:

- every material code change has a truthful rationale;
- every acceptance criterion has sufficient evidence;
- risk and non-goal claims agree with the implementation;
- no stale SHA, superseded check, or future step is described as completed;
- deferred work has a durable record rather than a vague follow-up promise.

A materially false or stale description fails review even when the code is
otherwise sound, because future maintainers would receive a false account of
why the system behaves as it does. Cosmetic wording and stylistic preference do
not block.

The PR body links authoritative design and decision records rather than copying
them. DESIGN remains the living authority; the PR explains how this change
instantiates it.

## Identity and mutation

Code identity and narrative identity are separate inputs to one review record:

- exact base/head/tree bind the implementation;
- a canonical body digest binds the reviewed explanation and acceptance trace.

Editing the title or body after attestation invalidates that evidence and
requires deterministic policy validation plus a refreshed semantic attestation
when the edit can change scope, rationale, risk, or acceptance mapping. The
existing App-owned exact-head check is not evidence for unreviewed metadata just
because the source SHA stayed unchanged.

## Authoring workflow

Open a draft PR early so cheap CI can run. Populate intent and acceptance rows
from the frozen plan, then update concrete evidence as implementation settles.
Before frontier review, a deterministic policy check verifies required
sections, criterion coverage, exact SHA references, and unresolved-thread state.

Upstroke may generate the first draft, but generation is not approval. The final
text is reviewed on the same terms whether written by Upstroke or a person.

## Acceptance criteria

1. Every material change in a sample PR maps to one rationale and at least one
   acceptance/risk/non-goal record.
2. Every frozen acceptance criterion appears exactly once in the trace or has a
   justified group mapping.
3. The policy check rejects missing sections, stale exact-SHA claims, and
   unaccounted criteria before model review.
4. A material body edit invalidates the prior narrative evidence without
   allowing candidate code to mint the trusted replacement.
5. Review evidence records both the code tuple and canonical body digest.
6. Deferred findings link to stable backlog records with regression status.
7. A human can understand what changed and why without reading the complete
   implementation diff first.

## Non-goals

- making prose length a quality gate;
- repeating DESIGN or the plan inside every PR;
- treating generated text as authoritative;
- requiring one row per trivial line edit;
- replacing exact code review with narrative review.

## Open questions for council

1. Which sections belong in every PR versus only high-risk changes?
2. Should criterion IDs be assigned during plan normalization?
3. Which metadata edits require semantic re-review versus deterministic body
   validation only?
4. How should stacked PRs inherit or specialize acceptance traces?
