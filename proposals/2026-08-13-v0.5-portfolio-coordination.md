*Original status block:*
**Status:** Proposal / Future Backlog Candidate
**Target:** Approximately v0.5
**Primary objective:** Coordinate multiple active stories as one engineering portfolio, identifying shared work, hidden dependencies, likely conflicts, and useful parallelism both before execution and while agents are actively working.

## 1. Executive Summary

Tactus should eventually support running multiple engineering stories concurrently.

Each story may have its own:

- design;
- requirements;
- acceptance criteria;
- implementation tasks;
- dependency DAG;
- assigned agents;
- verification pipeline.

However, story boundaries do not guarantee implementation independence.

Two stories may:

- modify the same files;
- change the same state machine;
- depend on the same new abstraction;
- introduce competing versions of the same component;
- alter the same schema or public API;
- contain duplicate implementation work;
- be logically independent but operationally unsafe to execute simultaneously.

Running every story-local DAG independently would therefore create avoidable:

- duplicated work;
- merge conflicts;
- semantic conflicts;
- architectural inconsistency;
- discarded implementations;
- repair tasks;
- model-capacity waste;
- human intervention.

Tactus should add a portfolio-level coordination layer above individual story plans.

The proposed architecture has two major phases:

```
Design-time portfolio reconciliation
        ↓
Runtime portfolio coordination
```

At design time, Tactus compares the implementation plans for all stories entering the active portfolio and constructs a global execution topology.

At runtime, Tactus continuously refines that topology using:

- agent execution intents;
- predicted write sets;
- actual changed paths;
- candidate diffs;
- integration results;
- verification failures;
- merge conflicts.

The central principle is:

**Plan globally, execute incrementally, and continuously replace predictions with observed reality.**

This feature should not be a prerequisite for initial parallel execution.

Earlier versions should establish:

- reliable single-story DAG execution;
- isolated workers and worktrees;
- verified candidates;
- merge queues;
- task footprints;
- actual changed-path telemetry;
- stable story and task identities.

The complete portfolio coordinator can then be introduced once Tactus has enough operational evidence to understand how real conflicts occur.

## 2. Motivation

A story is primarily a product and planning boundary.

It represents an intended outcome such as:

```
Add container-based execution.
```

or:

```
Implement crash-safe merge recovery.
```

A story is not necessarily an implementation-isolation boundary.

For example:

```
Story A
Extract scheduler logic from engine.rs

Story B
Add AwaitingMerge task state

Story C
Improve crash-resume reconciliation
```

These are separate product outcomes, but all may alter:

- task-state semantics;
- readiness calculation;
- persistence events;
- engine recovery;
- integration sequencing.

If their plans are executed independently, three agents may each redesign part of the same lifecycle model.

Each implementation may be locally reasonable while being mutually incompatible.

The same issue appears at smaller scales:

```
Story D
Introduce Runner abstraction

Story E
Move subprocess execution behind an execution interface
```

These may be duplicate descriptions of substantially the same underlying work.

Or:

```
Story F
Add Docker runner

Story G
Add Docker runner configuration
```

These may be better assigned to the same session because they share substantial context, despite being technically separable.

A portfolio coordinator allows Tactus to reason across these boundaries before capacity is spent.

## 3. Product Vision

A future Tactus run may begin with several selected stories:

```
$ tactus run-portfolio release-v0.5.toml
```

Tactus would:

1. load each story and its acceptance criteria;
2. design or load each story-local implementation DAG;
3. compare every active story with the others;
4. identify duplicate and shared work;
5. add missing cross-story dependencies;
6. identify predicted contention;
7. identify useful task affinity;
8. construct a global execution topology;
9. admit a safe and useful set of tasks;
10. assign agents and isolated workers;
11. compare live execution intents;
12. adjust scheduling as scopes change;
13. integrate verified candidates through the merge queue;
14. evaluate each story against its own acceptance criteria.

The result should look conceptually like:

```
Story A DAG       Story B DAG       Story C DAG
     │                 │                 │
     └─────────────────┼─────────────────┘
                       ▼
             Portfolio Reconciler
                       │
      ┌────────────────┼────────────────┐
      │                │                │
 shared work     cross-story deps   contention
      │                │                │
      └────────────────┼────────────────┘
                       ▼
             Global Execution Graph
                       │
                       ▼
             Runtime Coordinator
                       │
             safe parallel batches
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
       Worker A      Worker B      Worker C
          │            │            │
          └────────────┼────────────┘
                       ▼
                  Merge Queue
                       │
                       ▼
             Per-Story Acceptance
```

## 4. Goals

The portfolio coordinator should:

1. compare implementation plans across multiple stories;
2. identify duplicated or substantially overlapping work;
3. extract shared prerequisite tasks;
4. add missing cross-story dependencies;
5. predict file, subsystem, symbol, schema, and invariant contention;
6. identify tasks that may benefit from shared context or the same session;
7. construct sensible parallel execution waves;
8. prevent obviously conflicting work from running concurrently;
9. compare execution intents from active agents;
10. adapt when agents discover broader or different scope;
11. use actual changed paths and integration outcomes as ground truth;
12. preserve story-level traceability and acceptance criteria;
13. maintain deterministic and auditable scheduling decisions;
14. integrate with agent routing, capacity management, and merge coordination;
15. collect evidence that improves future conflict prediction.

## 5. Non-Goals

The initial portfolio coordinator should not:

- autonomously rewrite product requirements;
- merge stories merely because their implementations overlap;
- silently discard story acceptance criteria;
- use majority model opinion as proof of correctness;
- guarantee that predicted-safe tasks cannot conflict;
- rely exclusively on model-generated path predictions;
- pause or terminate active agents without an explicit policy;
- create uncontrolled replanning loops;
- compare the entire historical backlog on every scheduling decision;
- replace deterministic Git conflict detection;
- replace verification or review;
- make runtime scheduling responsible for architectural redesign;
- require learned or statistical conflict prediction in its first release.

The system coordinates execution.

It does not redefine what the product is supposed to do.

## 6. Terminology

### 6.1 Story

A product-level unit of intended value with its own:

- requirements;
- acceptance criteria;
- priority;
- status;
- implementation plan.

### 6.2 Task

An executable unit of engineering work.

Tasks belong to one or more stories and may have dependency relationships.

### 6.3 Story-Local DAG

The dependency graph produced for one story.

It describes the order in which that story's tasks can logically be completed.

### 6.4 Portfolio

The bounded set of stories currently being considered for coordinated execution.

The portfolio is not necessarily the entire backlog.

### 6.5 Global Execution Graph

The combined graph produced from all active story-local DAGs plus cross-story relationships.

### 6.6 Task Footprint

A structured prediction of the files, symbols, subsystems, APIs, schemas, invariants, and other resources a task may affect.

### 6.7 Execution Intent

A worker's current understanding of how it expects to implement a task after inspecting the repository.

### 6.8 Contention

A relationship indicating that two tasks may be logically independent but should not normally execute concurrently.

### 6.9 Affinity

A relationship indicating that two tasks may benefit from being assigned to the same worker, model family, or resumed session.

### 6.10 Shared Task

A task whose output supports requirements from more than one story.

### 6.11 Portfolio Reconciliation

The design-time process that combines multiple story-local plans into one global execution topology.

### 6.12 Runtime Coordination

The ongoing process of adjusting dispatch decisions using live and observed execution evidence.

## 7. Core Principles

### 7.1 Story Boundaries Are Not Isolation Boundaries

Stories remain separate for product intent and acceptance.

Their implementations may still overlap.

### 7.2 Dependency and Contention Are Different

A dependency means:

Task B cannot correctly complete before Task A.

Contention means:

Task A and Task B may be logically independent, but executing them simultaneously creates significant integration risk.

These must not be represented as the same edge type.

### 7.3 Predictions Are Scheduling Hints

Predicted footprints and semantic conflict assessments are useful but fallible.

They do not override:

- actual changed paths;
- Git integration results;
- deterministic verification;
- independent review.

### 7.4 Runtime May Change Scheduling, Not Product Intent

Runtime coordination may:

- hold;
- defer;
- serialise;
- reprioritise;
- cancel unstarted work;
- request replanning.

It should not silently:

- merge stories;
- remove acceptance criteria;
- redefine requirements;
- expand story scope.

### 7.5 Actual Evidence Replaces Predicted Evidence

Evidence should gain authority as work progresses:

```
design prediction
        ↓
worker execution intent
        ↓
actual changed paths
        ↓
candidate diff
        ↓
integration result
        ↓
post-merge verification
```

### 7.6 Portfolio Scope Must Be Bounded

Tactus should reconcile an active portfolio window rather than continuously comparing every item in the full backlog.

### 7.7 Every Coordination Decision Must Be Explainable

Tactus should be able to answer:

- why two tasks were serialised;
- why two tasks were combined into shared work;
- why a story was not admitted;
- why a worker was paused or deferred;
- which evidence caused a relationship to change.

## 8. Graph Model

A single dependency DAG is insufficient for portfolio coordination.

Tactus should represent several relationship types.

## 9. Dependency Edges

```
A → B
```

Meaning:

B requires A's result.

Dependencies may cross story boundaries.

Example:

```
Story B / Add container-backed Codex execution
depends on
Story A / Introduce Runner abstraction
```

Dependency edges affect logical readiness.

A task with unmet dependencies is not runnable.

## 10. Contention Edges

```
A ~ B
```

Meaning:

A and B are logically runnable, but should not normally execute at the same time.

Potential causes:

- predicted file overlap;
- same symbol or type;
- same state machine;
- same database schema;
- same migration;
- same public API;
- same configuration format;
- contradictory architectural assumptions;
- known merge hotspot;
- high historical semantic-conflict rate.

Contention affects dispatch eligibility but does not necessarily change story dependencies.

## 11. Affinity Edges

```
A ≈ B
```

Meaning:

A and B may benefit from shared context.

Potential actions:

- assign to the same worker session;
- dispatch sequentially to the same model;
- preserve a warm repository context;
- group into one implementation cluster;
- share a design or investigation stage.

Example:

```
Add Docker runner
Add Docker runner tests
Add Docker runner configuration
```

These tasks may be technically independent but cheaper and more coherent when handled together.

Affinity should initially be advisory.

It should not override hard isolation or reviewer-independence policy.

## 12. Overlap or Equivalence Edges

```
A ≡ B
```

Meaning:

A and B appear to describe substantially the same implementation work.

Example:

```
Task A
Introduce Runner abstraction

Task B
Move subprocess execution behind an execution interface
```

Possible resolution:

- merge into a shared task before execution;
- retain separate story requirement links;
- preserve separate story acceptance checks.

Overlap should initially require explicit approval or high-confidence policy.

Runtime should not merge already active tasks automatically.

## 13. Relationship Metadata

Every relationship should record:

```rust
struct TaskRelationship {
    id: RelationshipId,
    left: GlobalTaskId,
    right: GlobalTaskId,
    kind: RelationshipKind,
    confidence: Confidence,
    source: RelationshipSource,
    evidence: Vec<RelationshipEvidence>,
    created_at: Timestamp,
    supersedes: Option<RelationshipId>,
}
```

Potential sources:

```rust
enum RelationshipSource {
    Human,
    StoryDesigner,
    PortfolioReconciler,
    DeterministicPathAnalysis,
    RepositoryMap,
    SemanticReview,
    WorkerIntent,
    ActualChangedPaths,
    CandidateDiff,
    MergeResult,
    VerificationResult,
}
```

Later evidence should supersede earlier predictions rather than mutating history invisibly.

## 14. Evidence Precedence

Recommended precedence:

```
Merge and verification results
        >
candidate diff
        >
actual changed paths
        >
live execution intent
        >
semantic prediction
        >
deterministic pre-execution prediction
```

A low-confidence design-time contention edge may be removed after both tasks publish clearly disjoint execution intents.

A predicted-safe relationship may become contended when one worker expands its scope.

## 15. Design-Time Portfolio Reconciliation

Portfolio reconciliation occurs after story-local plans exist but before implementation capacity is committed.

Input:

```
selected stories
+
story requirements
+
acceptance criteria
+
story-local DAGs
+
repository architecture map
+
known decisions and invariants
+
current integration state
```

Output:

```
global execution graph
+
shared tasks
+
cross-story dependencies
+
contention relationships
+
affinity relationships
+
recommended execution waves
+
unresolved coordination questions
```

## 16. Story-Local Design

Each story should first be understandable in isolation.

A story designer produces:

- story implementation approach;
- tasks;
- dependencies;
- predicted task footprints;
- affected architecture decisions;
- acceptance mapping.

Example:

```
Story A — Extract Scheduler

A1 Define scheduler boundary
A2 Extract readiness calculation
A3 Move scheduler-specific tests
A4 Preserve engine public API
```

This local plan remains useful even after portfolio reconciliation modifies execution relationships.

## 17. Portfolio Reconciliation Pass

The portfolio reconciler compares all active stories and asks:

1. Do any stories contain duplicate implementation work?
2. Do multiple stories need the same prerequisite?
3. Are there hidden cross-story dependencies?
4. Do tasks modify the same files or symbols?
5. Do tasks alter the same architectural invariant?
6. Do separate stories propose contradictory abstractions?
7. Would one task make another substantially easier?
8. Should related tasks be assigned to one context-rich session?
9. Which tasks are genuinely safe to execute in parallel?
10. Which stories should be delayed until high-contention work completes?

## 18. Shared Prerequisite Extraction

Suppose three stories all need a stable lifecycle abstraction.

The reconciler may create:

```
Shared Task S1
Extract and formalise task lifecycle state machine
```

Then:

```
Story A tasks
      └── depend on S1

Story B tasks
      └── depend on S1

Story C tasks
      └── depend on S1
```

S1 should link to requirements in each affected story.

Completing S1 does not complete those stories.

It only satisfies part of their implementation requirements.

## 19. Duplicate Work Reconciliation

When two tasks substantially overlap, the reconciler should produce a recommendation:

```
Potential overlap

Task A:
Introduce Runner trait

Task B:
Abstract subprocess execution

Confidence:
High

Recommendation:
Replace A and B with shared task S2.

Affected requirements:
Story A / requirement A-2
Story B / requirement B-1
```

The initial version should not silently apply ambiguous merges.

Possible policies:

```
manual
high-confidence-auto
recommend-only
```

The default should initially be conservative.

## 20. Cross-Story Dependency Discovery

A dependency may be absent because each story was designed independently.

Example:

```
Story B:
Add container-backed agents

Story A:
Introduce execution Runner interface
```

Story B may be implementable without Story A in theory, but doing so first would likely create duplicate or temporary architecture.

The reconciler can add:

```
A.RunnerAbstraction → B.ContainerBackend
```

The relationship should explain whether it is:

- a hard correctness dependency;
- an architectural sequencing preference;
- a simplification dependency.

Only hard dependencies should block logical readiness permanently.

Architectural sequencing preferences may instead become high-confidence contention or dispatch-order constraints.

## 21. Predicted Execution Waves

The reconciler may group work into waves.

Example:

```
Wave 1
- Task-state extraction
- Codex telemetry changes
- Documentation updates

Wave 2
- Merge queue
- Resume reconciliation
- Candidate persistence

Wave 3
- Parallel dispatcher
- Dynamic contention coordinator
```

Waves are not necessarily rigid phases.

They are suggested admission groups based on:

- dependency completion;
- contention;
- downstream unblocking value;
- priority;
- available workers;
- expected integration pressure.

## 22. Story Admission Control

Not every ready story should enter the active portfolio immediately.

Suppose ten stories are ready but five affect the same engine state machine.

Tactus may admit:

```
Story A
Story D
Story F
```

while deferring:

```
Story B
Story C
Story E
```

until shared prerequisites or high-contention tasks complete.

Admission decisions should consider:

- story priority;
- deadline;
- blocked downstream work;
- subsystem contention;
- merge queue pressure;
- agent capacity;
- expected task duration;
- current active footprints.

Admission control prevents the active portfolio from becoming larger than Tactus can coordinate effectively.

## 23. Runtime Coordination

Design-time reconciliation remains predictive.

Agents frequently discover that implementation scope differs from the plan.

Runtime coordination therefore maintains a live portfolio view.

Conceptually:

```
Global execution graph
        ↓
Runnable frontier
        ↓
Initial dispatch selection
        ↓
Workers inspect repository
        ↓
Execution intents
        ↓
Live contention graph
        ↓
Updated dispatch and hold decisions
        ↓
Actual diffs
        ↓
Merge and verification results
        ↓
Graph refinement
```

## 24. Inspect-Before-Write Phase

For tasks above a configurable risk threshold, a worker should initially inspect the repository before beginning implementation.

The worker then publishes an execution intent.

Example:

```
Task:
Extract scheduler

Current understanding:
Move task readiness and runnable-node selection out of engine.rs.

Expected files:
- src/engine.rs
- src/engine/scheduler.rs
- src/engine/mod.rs

Expected symbols:
- Engine::run
- runnable_tasks
- TaskState

Semantic footprint:
- task readiness
- dependency completion
- scheduler ownership

Affected decisions:
- task lifecycle
- parallel dispatch
```

The task may then receive permission to proceed.

This creates a more accurate conflict view than design-time prediction alone.

## 25. Execution Intent Schema

Conceptually:

```rust
struct ExecutionIntent {
    task_id: GlobalTaskId,
    attempt_id: AttemptId,
    revision: u32,

    summary: String,

    expected_paths: Vec<PathPattern>,
    expected_symbols: Vec<SymbolRef>,
    expected_subsystems: Vec<SubsystemId>,
    expected_invariants: Vec<InvariantId>,
    expected_schema_changes: Vec<SchemaRef>,
    expected_api_changes: Vec<ApiRef>,

    implementation_steps: Vec<String>,
    discovered_dependencies: Vec<GlobalTaskId>,
    discovered_conflicts: Vec<GlobalTaskId>,

    confidence: Confidence,
    published_at: Timestamp,
}
```

Execution intents should be persisted and versioned.

A worker may revise its intent after further investigation.

## 26. Live Intent Comparison

The contention coordinator compares intents across all active tasks, regardless of story.

Example:

```
Task A2
Expected paths:
- engine.rs
- scheduler.rs

Semantic footprint:
- readiness
- dependency completion
```

```
Task B1
Expected paths:
- events.rs
- engine.rs

Semantic footprint:
- AwaitingMerge
- readiness
- lifecycle transitions
```

Result:

```
File overlap:
engine.rs

Semantic overlap:
readiness
task lifecycle

Risk:
High

Action:
Allow A2 to proceed.
Hold B1 until A2 produces a candidate.
```

The action should be auditable and policy-driven.

## 27. Intent Updates

A worker may discover additional scope:

```
Original intent:
modify codex.rs

Updated intent:
modify codex.rs, execution.rs, config.rs
```

The coordinator should recompute contention when:

- an intent is first published;
- an intent changes materially;
- a task begins writing;
- changed paths are observed;
- a candidate is produced.

Intent revisions should not silently replace prior versions.

## 28. Runtime Coordination Actions

Potential actions:

```rust
enum CoordinationAction {
    Proceed,
    ProceedWithWarning,
    Hold,
    SerializeAfter(GlobalTaskId),
    PreferSameSession(GlobalTaskId),
    CancelBeforeMutation,
    RequestReplan,
    EscalateToHuman,
}
```

The initial release should be conservative.

Recommended behaviour:

- freely hold unstarted tasks;
- serialise tasks before implementation begins;
- avoid cancelling tasks that have already performed substantial work;
- do not pause an agent mid-write unless risk is critical;
- use the merge queue and candidate verification as the final safety boundary.

## 29. Task Progress Awareness

Conflict response should consider task progress.

Example policy:

```
No implementation started
→ safe to hold or cancel

Repository explored, no writes
→ usually safe to hold

Small uncommitted diff
→ cancellation possible with policy

Large candidate near completion
→ prefer allowing completion and resolving at integration

Verified immutable candidate
→ never mutate; integrate or supersede
```

Coordination should minimise wasted work without compromising correctness.

## 30. Deterministic Conflict Detection

The first conflict layer should be cheap and deterministic.

Signals include:

- exact path overlap;
- path-pattern overlap;
- same generated file;
- same schema;
- same migration directory;
- same package manifest;
- same public interface;
- explicit exclusive resource;
- manually declared conflict;
- shared candidate base.

Deterministic checks should run before expensive semantic analysis.

## 31. Semantic Conflict Detection

Some conflicts do not share files.

Example:

```
Task A
Change Completed to mean verified candidate.

Task B
Update resume logic assuming Completed means merged.
```

Different files may be changed, but the tasks affect the same invariant.

Semantic analysis should inspect:

- task descriptions;
- designs;
- execution intents;
- affected decisions;
- architecture map;
- predicted symbols;
- acceptance criteria.

Its output should be structured:

```
Relationship:
Contention

Confidence:
High

Reason:
Both tasks redefine task completion semantics.

Suggested action:
Serialise A before B.
```

Semantic predictions remain advisory until supported by actual execution evidence.

## 32. Repository Architecture Map

Portfolio coordination benefits from a lightweight repository map.

Potential contents:

```
modules
subsystems
public APIs
important symbols
schemas
migrations
configuration formats
architecture decisions
core invariants
known hotspots
generated-code boundaries
```

Tasks can reference this map in footprints and intents.

The map does not need to be perfect.

Its purpose is to make semantic overlap easier to identify.

## 33. Task Footprints

A common footprint structure should support design-time and runtime reasoning.

```rust
struct TaskFootprint {
    paths: Vec<PathPattern>,
    symbols: Vec<SymbolRef>,
    subsystems: Vec<SubsystemId>,
    invariants: Vec<InvariantId>,
    schemas: Vec<SchemaRef>,
    apis: Vec<ApiRef>,
    exclusive_resources: Vec<ResourceId>,
}
```

Footprints may be:

- predicted by the story designer;
- refined by the portfolio reconciler;
- updated by execution intent;
- replaced by actual observed footprints.

Every footprint should record provenance.

## 34. Actual Changed Paths

Once an attempt produces a diff, actual changed paths become authoritative for file-level analysis.

Tactus should record:

```
paths added
paths modified
paths deleted
renames
binary changes
generated files
submodules
```

Actual changed paths should:

- update contention knowledge;
- inform future dispatch;
- influence merge ordering;
- provide telemetry for prediction quality.

## 35. Candidate Diff Analysis

A candidate diff may reveal semantic scope not represented by paths alone.

Tactus may extract:

- changed public APIs;
- changed event schemas;
- changed state transitions;
- changed configuration keys;
- changed dependency manifests;
- changed architecture decisions;
- new migration files.

This can trigger new holds before conflicting tasks are dispatched.

## 36. Integration as Ground Truth

The merge queue determines whether verified candidates actually integrate.

Outcomes include:

```
clean integration
textual conflict
semantic gate failure
review failure after stale rebase
already-present change
repair task required
candidate superseded
```

These outcomes should feed back into the portfolio graph.

Example:

```
Predicted contention:
Low

Actual result:
Semantic integration failure

Future evidence:
Increase contention for similar task/subsystem combinations.
```

## 37. Global Scheduling

The scheduler should not simply launch every runnable node.

It should request a dispatch plan from the portfolio coordinator.

Conceptually:

```
Scheduler
- computes logically runnable tasks

Portfolio Coordinator
- removes or orders contended tasks
- applies story admission policy
- considers active intents
- considers merge pressure

Router
- assigns eligible agents

Execution Runtime
- launches isolated workers
```

This keeps responsibilities distinct.

## 38. Dispatch Selection

A conceptual dispatch score may include:

```
dispatch value =
    story priority
  + downstream unblocking value
  + expected completion value
  + capacity efficiency
  + affinity benefit
  - contention risk
  - merge risk
  - expected repair cost
  - integration queue pressure
```

The first implementation should use transparent heuristics.

A sophisticated optimiser is not required.

## 39. Safe Parallel Set

The portfolio coordinator attempts to choose a useful set of tasks that:

- are logically runnable;
- satisfy hard policies;
- do not have active high-confidence contention;
- fit concurrency limits;
- use available agent capacity;
- avoid overloading the merge queue.

This resembles selecting an independent set from a conflict graph, but the initial implementation does not need mathematically optimal scheduling.

A deterministic greedy policy is sufficient.

## 40. Fairness Across Stories

Without fairness, one large story may monopolise workers.

Possible policies:

```
priority-weighted fairness
round-robin across stories
maximum workers per story
reserved critical-story slots
deadline mode
```

Fairness should remain subordinate to hard dependencies and critical contention.

## 41. Router Integration

The portfolio coordinator decides:

Which tasks are sensible to dispatch?

The routing engine decides:

Which eligible agent should perform each selected task?

Routing may consider portfolio metadata:

- affinity cluster;
- required repository context;
- expected task duration;
- implementation risk;
- story priority;
- model-family diversity;
- available subscription capacity.

Example:

```
Tasks A and B have strong affinity.

Router decision:
Assign both sequentially to the same resumed session.
```

Affinity must not weaken independent review requirements.

## 42. Merge Queue Integration

All stories should ultimately integrate through a shared authoritative merge process.

The merge queue should know:

- story ownership;
- task ownership;
- shared-task links;
- candidate base;
- active contention;
- dependent tasks;
- priority;
- stale-candidate status.

Story boundaries should not produce separate inconsistent integration heads unless explicitly supported as separate portfolios.

## 43. Story Completion

A story should be complete only when:

1. all required tasks are merged or otherwise satisfied;
2. shared tasks linked to the story are merged;
3. story-specific acceptance criteria pass;
4. required reviews complete;
5. no unresolved critical coordination finding remains;
6. the result is present on the current authoritative integration head.

A task completing in another story may satisfy a requirement without completing the whole story.

## 44. Shared Task Traceability

A shared task must preserve requirement-level links.

Example:

```
Shared Task S1
Introduce Runner abstraction

Satisfies:
- Story A / requirement A-2
- Story B / requirement B-1
- Story C / prerequisite C-P1
```

The audit trail should show:

- why the task was shared;
- which original tasks it superseded;
- which stories depend on it;
- which acceptance criteria still remain.

## 47. Crash Recovery

Portfolio coordination introduces additional recovery requirements.

After restart, Tactus must reconstruct:

- admitted stories;
- global task graph;
- active task relationships;
- current execution intents;
- held tasks;
- active workers;
- verified candidates;
- merge queue state;
- current integration head;
- story acceptance state.

Recovery must distinguish:

```
task was held but never started
task was dispatched but worker disappeared
task produced unrecorded filesystem changes
candidate exists but event was not written
relationship was proposed but not accepted
```

Authoritative Git and event state remain the sources of truth.

## 48. Reconciliation After Restart

On restart, Tactus should:

1. load the persisted portfolio graph;
2. inspect active worker state;
3. inspect candidate refs and worktrees;
4. reconcile actual integration head;
5. invalidate stale live intents where appropriate;
6. regenerate deterministic contention indexes;
7. resume or replace interrupted tasks;
8. create a new dispatch plan.

It should not simply rerun portfolio design and silently produce a different graph.

Material replanning should be explicit and versioned.

## 49. Plan Versioning

Portfolio plans should be immutable revisions.

Example:

```
Portfolio Plan v1
- initial reconciliation

Portfolio Plan v2
- shared Runner task introduced

Portfolio Plan v3
- runtime discovery added cross-story dependency
```

Each revision should record:

- trigger;
- changed relationships;
- changed tasks;
- affected stories;
- decision source;
- approval status.

## 50. Runtime Replanning Boundary

Runtime may discover that the plan is materially wrong.

Example:

```
Task B cannot proceed without redesigning a shared API.
```

The coordinator should not improvise a large architecture change.

It should emit:

```
PortfolioReplanRequested
```

with:

- affected stories;
- discovered conflict;
- blocked tasks;
- relevant diffs and intents;
- recommended planning question.

A design or human approval phase can then produce a new plan revision.

## 51. Scalability

Comparing every task against every other task produces approximately quadratic growth.

That is acceptable for small portfolios but not large ones.

Tactus should use staged candidate generation.

## 52. Deterministic Candidate Clustering

First cluster tasks using cheap metadata:

- predicted paths;
- subsystems;
- symbols;
- schemas;
- APIs;
- invariants;
- architecture decisions;
- story tags;
- repository areas.

Example:

```
Cluster 1
engine lifecycle

Cluster 2
Codex adapter

Cluster 3
container execution

Cluster 4
documentation
```

Semantic comparison then focuses on tasks within likely-overlap clusters.

Broad tasks may belong to multiple clusters.

## 53. Semantic Comparison Budget

Portfolio semantic analysis should be bounded.

Potential controls:

```
maximum active stories
maximum active tasks
maximum semantic comparisons
maximum reconciliation passes
maximum model capacity
```

The system should report when analysis was truncated or used conservative fallback rules.

Unknown should not be presented as safe.

## 54. Conservative Fallback

When Tactus cannot confidently assess conflict:

```
critical task + unknown overlap
→ serialise conservatively

low-risk task + strong verification
→ allow with warning

weak verification + broad scope
→ hold or request review
```

Policy should depend on risk and verification strength.

## 62. Parallel Efficiency

Raw concurrency is not the goal.

```

integration queue pressure

```

A portfolio coordinator is successful if it increases accepted throughput, even if it occasionally runs fewer tasks at once.

## 63. Future Learning

The first portfolio coordinator should use explicit heuristics and structured review.

Later, Tactus may learn:

- which task pairs frequently conflict;
- which modules are integration hotspots;
- which footprint predictions are reliable;
- which affinity clusters improve completion;
- which agents tend to expand scope;
- when parallel execution causes repair work;
- when conservative serialisation was unnecessary.

This may eventually become a contextual scheduling problem.

Learning is not required for the initial design.

Telemetry should be collected from the beginning.

## 64. Interaction With Design Councils

For major portfolios, a structured design review may produce:

```
story-local designs
+
implementation DAGs
+
predicted footprints
+
cross-story relationship proposals
+
portfolio risks
```

A separate decomposition review can ask:

- are tasks unnecessarily fragmented?
- are shared prerequisites missing?
- are stories making incompatible assumptions?
- is proposed parallelism unsafe?
- should certain tasks share one implementation context?

The portfolio coordinator consumes the approved result.

It should not depend on any particular design process.

## 65. Interaction With Execution Isolation

Each running task should remain isolated in its own worker and worktree unless a future explicit shared-session mode is used.

Portfolio coordination does not replace isolation.

Isolation protects:

- repository state;
- worker state;
- credentials;
- host resources.

Coordination reduces expected integration waste.

Both are required.

## 66. Interaction With Verification

Coordination predictions must never weaken verification.

The pipeline remains:

```
portfolio selects task
        ↓
router selects agent
        ↓
isolated implementation
        ↓
candidate capture
        ↓
deterministic gates
        ↓
independent review
        ↓
merge queue
        ↓
story acceptance
```

A task being judged "safe to parallelise" does not make its output trusted.

## 67. Interaction With Capacity Management

Portfolio scheduling should consider available model and provider capacity.

Example:

```
Several safe independent tasks are runnable.

Available capacity:
- implementation pool A: high
- implementation pool B: low
- review pool: saturated

Decision:
dispatch fewer implementation tasks to avoid overwhelming review and merge.
```

The bottleneck may be:

- implementers;
- reviewers;
- gates;
- merge queue;
- human approvals.

The portfolio coordinator should avoid producing work faster than the trusted integration path can absorb it.

## 77. Risks

### 77.1 Excessive Conservatism

The coordinator may serialise too much work and erase parallelism gains.

Mitigations: confidence thresholds; strong-vs-advisory contention; prediction-quality telemetry; allow-with-warning policy for well-tested tasks; actual outcome feedback.

### 77.2 Missed Semantic Conflict

Tasks may appear independent but conflict after integration.

Mitigations: execution intents; semantic footprint analysis; immutable candidates; merge-time re-verification; repair tasks; independent review.

### 77.3 Unnecessary Planning Cost

Portfolio analysis may consume more capacity than it saves.

Mitigations: bounded active portfolio; deterministic clustering; semantic analysis only for likely overlap; risk-based planning depth; compare coordination cost with avoided rework.

### 77.4 Story Intent Becomes Blurred

Shared tasks may make it unclear which story owns which outcome.

Mitigations: requirement-level links; separate story acceptance; immutable provenance; no automatic story merging.

### 77.5 Runtime Coordinator Becomes a Hidden Project Manager

The coordinator may begin redefining scope rather than scheduling work.

Mitigations: strict runtime authority boundaries; explicit replanning events; plan revision approval; runtime may change timing, not requirements.

### 77.6 Stale Execution Intents

Workers may publish an intent and then perform different work.

Mitigations: intent revisions; actual changed-path capture; candidate analysis; policy requiring intent updates for material scope expansion.

### 77.7 Mid-Execution Cancellation Wastes Work

Dynamic contention may be discovered after substantial progress.

Mitigations: inspect-before-write phase; progress-aware coordination actions; prefer integration handling when work is nearly complete; cancel only under explicit policy.

### 77.8 Quadratic Comparison Cost

Large portfolios may generate too many task pairs.

Mitigations: bounded portfolio windows; deterministic indexing; subsystem clustering; compare only likely-overlap candidates.

### 77.9 Coordination State Complicates Recovery

Holds, intents, relationships, and plan revisions add persistence complexity.

Mitigations: event-sourced decisions; immutable plan revisions; authoritative Git state; explicit recovery acceptance tests.

### 77.10 Gaming or Misleading Intents

A worker may underestimate scope or fail to identify likely conflicts.

Mitigations: intents are predictions, not authority; compare with actual changes; track scope-expansion frequency; keep verification and merge isolation authoritative.

## 81. Strategic Value

Most multi-agent systems focus on increasing the number of workers.

That creates an increasingly important secondary problem:

Which work should actually be allowed to happen at the same time?

A portfolio coordinator gives Tactus a larger role than merely launching agents.

It becomes responsible for organising engineering work across:

- stories;
- tasks;
- models;
- workers;
- dependencies;
- shared abstractions;
- integration constraints;
- limited review and merge capacity.

The differentiation is not:

Tactus can run ten agents.

It is:

Tactus can examine ten stories, recognise that only six tasks are usefully independent, extract two shared prerequisites, preserve three story acceptance boundaries, and dispatch the work in an order that maximises accepted progress rather than raw activity.

## 82. Long-Term Vision

A mature Tactus may be given a release portfolio containing:

```
parallel scheduler
container execution
merge recovery
adaptive routing telemetry
new agent adapter
documentation
```

Each story is independently designed.

The portfolio coordinator discovers:

- scheduler and merge recovery share lifecycle semantics;
- container execution and the new adapter share a Runner prerequisite;
- routing telemetry can proceed independently;
- documentation has affinity with completed implementation rather than active design;
- two tasks propose duplicate configuration abstractions.

Tactus produces a global plan:

```
Shared Task S1
Formalise lifecycle model

Shared Task S2
Introduce Runner abstraction

Parallel Wave A
- S1
- S2
- routing telemetry

Parallel Wave B
- merge recovery
- container backend

Parallel Wave C
- scheduler
- agent adapter

Final Wave
- integration documentation
- release acceptance
```

During execution, one worker discovers it must also modify the event schema.

Its execution intent changes.

Tactus detects contention with a queued resume task and delays that task.

After the candidate integrates, the delayed task receives the new authoritative context and proceeds without discarded work.

Every story is then evaluated independently against its acceptance criteria.

That is the intended end state:

A coordinated portfolio of autonomous engineering work, not merely a collection of parallel agents.

## 83. Recommendation

Treat full portfolio coordination as an approximately v0.5 capability.

Do not make it a prerequisite for the initial parallel scheduler.

Preserve the necessary foundations earlier:

- stable story and task identities;
- requirement traceability;
- task footprints;
- actual changed-path telemetry;
- cross-story-capable dependency representation;
- relationship provenance;
- immutable execution evidence;
- authoritative merge and acceptance semantics.

The architectural rule should be:

Design each story locally, reconcile active stories globally, coordinate running tasks dynamically, and let integration evidence remain authoritative.

This creates a natural progression from reliable task orchestration toward portfolio-level autonomous engineering coordination without forcing the earliest versions to solve every planning problem at once.
