# Review convergence and defect governance

**Status:** Draft
**Review:** Unreviewed
**Target:** v0.2 (manual policy immediately; automation after critical parallelism)
**Filed:** 2026-08-15
**Origin:** owner prompts during PR #14's extended review/fix cycle, 2026-08-15.

---

## Summary

Upstroke should optimize review for risk reduction and convergence, not for an
unbounded hunt that can always produce another concern. Each feature branch gets
a bounded review budget, every finding is classified and deduplicated, confirmed
bugs receive regression coverage or a durable guard, and non-blocking work moves
to an explicit backlog rather than silently expanding the feature.

The initial policy is manual. Automation should follow the critical parallel
execution work so process machinery does not delay the architecture it is meant
to accelerate.

## Review sequence

Run deterministic CI and acceptance gates first. A frontier review does not
start against a head that already fails cheaper evidence.

Each feature branch normally receives at most three semantic frontier review
invocations. Each item below is one seat and one invocation; an automatic
second opinion consumes the next slot rather than hiding inside a round:

1. **Broad candidate sweep.** One adversarial high-depth review searches the
   complete branch and affected invariants for concrete defects.
2. **Closure review.** An independent frontier review checks the fixes and
   challenges each surviving candidate against evidence.
3. **Conditional final closure.** Run only when round two confirms a
   branch-caused blocker or a fix regression. It verifies that bounded repair,
   not a newly expanded whole-repository hunt.

Today the manual binding is one Ultra-capable Codex sweep followed by Sol Max
closure. Those product names are an operational choice, not the durable
contract; Upstroke should eventually bind the two roles by capability and record
the concrete model afterward.

Idempotent recovery of the same interrupted provider invocation is not a new
judgment; dispatching a fresh model judgment is. An Ultra suggestion alone does
not start another fix loop. The closure review
must confirm a reproducible blocking defect, acceptance failure, or trust-boundary
violation. A disagreement without new evidence is recorded, not endlessly
re-litigated. An owner may authorize an exceptional fourth round only for a
credible severe security or irreversible-data-loss concern, and the reason is
part of the record.

## Finding record

Every review candidate receives a stable `finding_id` and these fields:

- exact branch/head, file and smallest useful location;
- concise failure sequence and evidence reference;
- provenance: `introduced`, `fix_regression`, or `pre_existing`;
- category, including at least security/trust, data integrity, correctness,
  concurrency, reliability, performance/resource, portability, test/CI,
  documentation/contract, and maintainability;
- confidence/state: candidate, confirmed, rejected, duplicate, fixed, deferred,
  or accepted risk;
- affected acceptance criterion or invariant;
- regression test name/reference, or a documented invariant/pitfall and the
  reason deterministic coverage is not practical;
- duplicate, recurrence, and first-bad links where known;
- disposition, target milestone, and reassessment history.

The rule is **find a bug once**. A recurrence links to the original finding and
its missing or insufficient guard; it is not counted as a novel discovery.

## Three-axis priority matrix

Only a confirmed finding is scored. Model-proposed numbers are claims; the
coordinator or human adjudicator owns the normalized score.

| Axis | Meaning | Scale |
|---|---|---|
| `C` | Category criticality: the inherent consequence class of the category | 1–10 |
| `S` | Severity within that category for this concrete failure | 1–10 |
| `L` | Likelihood, exploitability, or user-facing frequency | 1–10 |

The first proposed derived priority is versioned as:

```text
P = round(0.35 × C + 0.30 × S + 0.35 × L)
```

Policy floors prevent averages from understating asymmetric harm:

- a confirmed security/trust defect has `P >= 7`;
- security/trust with `S >= 7` has `P >= 9`;
- catastrophic compromise or breach with `S >= 9` has `P = 10`;
- irreversible data corruption or loss with `S >= 7` has `P >= 8`;
- a branch-caused CI or acceptance-criterion failure blocks regardless of its
  numeric score.

Scores are decision aids, not fake precision. Store the three inputs, algorithm
version, rationale, and confidence. Reassessment appends a new scored record;
it never overwrites the historical judgment.

## Disposition policy

- `P 7–10`: a branch-caused finding blocks the feature.
- `P 5–6`: fix when it affects an acceptance criterion or the touched
  invariant; otherwise defer explicitly.
- `P 1–4`: normally backlog with evidence.
- A pre-existing `P 9–10` issue triggers an urgent separate repair path. It does
  not silently absorb the feature branch unless the feature cannot safely ship
  around it.

A deferred record includes the C/S/L tuple, category, provenance, evidence,
acceptance link, regression status, deferral reason, owner, and target milestone.
Nothing disappears merely because the current PR is allowed to converge.

## Scope control

Review the branch diff and the invariants it can affect. A reviewer may report a
baseline bug discovered along that path, but it must be labelled `pre_existing`
and routed separately. Fixes remain the smallest coherent change that closes the
confirmed feature risk. Broad authority redesign, unrelated cleanup, and product
ideas become backlog or proposals.

## Acceptance criteria

1. CI precedes frontier spend on every reviewable head.
2. A branch cannot exceed three ordinary semantic frontier invocations.
3. Every fixed confirmed bug has a deterministic regression or a recorded
   coverage rationale and guard.
4. Duplicate and recurrent findings resolve to one stable identity.
5. Introduced, fix-regression, and pre-existing counts are independently
   reportable.
6. The C/S/L tuple and derived policy version are reproducible from the record.
7. A deferred issue remains discoverable with an owner/revisit condition.
8. A final review can return a clean pass; it is not required to manufacture a
   low-value observation.

## Relationship to finding telemetry

The companion [review-finding telemetry proposal](2026-08-13-v0.2-review-finding-telemetry.md)
records what a reviewer claimed. This proposal governs later confirmation,
deduplication, scoring, regression coverage, and disposition. Telemetry never
becomes authoritative merge policy merely because it is structured.

## Non-goals

- proving that three reviews find every defect;
- allowing a score to override an explicit acceptance failure;
- asking the same stochastic judge repeatedly until it returns PASS;
- automating the full policy before the parallel scheduler is usable;
- turning every pre-existing bug into feature-branch scope.

## Open questions for council

2. Is the proposed weighted formula preferable to a lookup matrix with explicit
   security/data overrides?
3. Which actor may mark a candidate `confirmed` or `accepted risk`?
4. When should the bounded-round exception require a human rather than another
