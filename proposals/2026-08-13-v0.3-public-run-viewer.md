# Public run viewer — tactus building tactus, with receipts

**Status:** Draft
**Target:** v0.3 (live board, with the dashboard); a static replay precursor is v0.2-era
**Filed:** 2026-08-13
**Origin:** owner idea, 2026-08-13, shaped in a Fable 5 assessment session.

---

## Summary

Once tactus has a clear UI, open a **read-only public view of tactus being built with tactus**: live (or replayed) runs showing tasks, attempts, models, gates, verdicts, merges, and real costs. The self-hosting decision already frames the claim — "N% of v0.2 was written by tactus" is a `git log --grep` result with receipts. This makes the receipts continuously legible to strangers.

Public CI logs did this for open-source trust; this is public CI for agent orchestration.

## Why it fits

- **Architecturally nearly free.** The v0.3 dashboard is already specced as a thin client folding `events.jsonl` (DESIGN.md §21). A public view is the same client with a publish filter. The engine still never speaks HTTP — a separate static viewer does the serving. No new invariants, no engine changes.
- **The demo nobody can fake.** Live cost-per-task, attempts, which model implemented, which family reviewed, what the reviewer rejected and why. It is also the enterprise "pen" pitch (DESIGN.md §23.1 — cross-vendor audit log, cost attribution, named reviewer) demonstrated as a product rather than claimed on a slide, using the same thin client that pitch would sell.
- **Stranger's scrutiny, institutionalized.** §23.1's sequencing rule says to use tactus on real work "until it would survive a stranger's scrutiny" — this feature *is* that scrutiny, standing. Publishing the miss log is on-brand for a project whose records print `?` instead of `$0.00` and separate measured from assumed.

## Shape

Two stages, deliberately ordered:

1. **Replay theater (v0.2-era, no backend).** Live state and replay are the same fold, so a finished run's scrubbed `events.jsonl` plus the client-side fold is a complete static page. Publish curated replays — including a failure run with its repair task, because that is the credibility moment. Zero uptime burden, ~90% of the value.
2. **Live board (v0.3, with the dashboard).** The same client pointed at a tail instead of a file. Arrives approximately for free once the dashboard exists.

## The two real work items hiding in "read-only"

1. **A public projection schema — not "the log with auth off."** The ops half of the run dir is not automatically publishable: gate logs and stderr tails carry absolute paths and usernames; question/answer text can carry anything; `run_started` records host paths. Define an explicit allowlist projection (event types and fields chosen for publication) plus a deterministic scrub pass — same philosophy as the secret-leak gate: regex, not judgment. Diffs and plans are fine; the repo is public anyway.
2. **A deliberate call on capacity data.** Pool estimates, reset windows, and spend-down engaging are the operator's actual subscription state — and a public board captioned "watch me optimally drain my Claude Max window" advertises exactly the gray zone §20 says to re-verify with providers before public launch. The costs themselves are the killer content and should stay ($X/task with receipts is the number that sells); the *pool mechanics* may warrant coarsening. If this ships, the §20 ToS re-check moves earlier on the roadmap.

## Boundary

**Publish Phase 2, not Phase 1.** Execution runs, verdicts, merges, costs — yes. Interactive design sessions are half-formed thinking with the user in the loop; their durable output is already public in `decisions/`. Stream the orchestra, not the rehearsal.

## Non-goals

- No interaction channel of any kind (no comments, no answer input — answers only ever arrive via `tactus answer` locally).
- No hosting obligation inside the engine; the viewer is a thin client and can be a static site.
- Not a monitoring product; it is a credibility and demo surface first.

## Open questions for council

1. Exact allowlist: which event types and which fields per type?
2. Is question/answer text publishable at all, or summarized/redacted by default?
3. How coarse should published capacity/pool data be, and does spend-down state appear?
4. Curated replays vs. publish-every-run: who curates, and by what rule?
5. Does the viewer share the dashboard codebase from day one, or does the replay theater ship first as a separate static page?
