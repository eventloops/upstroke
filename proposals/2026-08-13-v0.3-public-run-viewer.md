# Public run viewer — upstroke building upstroke, with receipts

**Status:** Draft
**Target:** v0.3 (live board, with the dashboard); a static replay precursor is v0.2-era
**Filed:** 2026-08-13
**Origin:** owner idea, 2026-08-13, shaped in a Fable 5 assessment session.

---

## Summary

Once upstroke has a clear UI, open a **read-only public view of upstroke being built with upstroke**: live (or replayed) runs showing tasks, attempts, models, gates, verdicts, merges, and real costs. The self-hosting decision already frames the claim — "N% of v0.2 was written by upstroke" is a `git log --grep` result with receipts. This makes the receipts continuously legible to strangers.

Public CI logs did this for open-source trust; this is public CI for agent orchestration.

## Why it fits

- **Architecturally close to the existing dashboard, but with a real publication boundary.** The v0.3 dashboard is already specced as a thin client folding `events.jsonl` (DESIGN.md §21). The engine still never speaks HTTP — a separate static viewer does the serving — and no engine change is required. Public projection nevertheless adds two load-bearing invariants: confidential run material is denied unless explicitly authorized for publication, and untrusted projected content is rendered as inert text rather than browser-active markup.
- **The demo nobody can fake.** Live cost-per-task, attempts, which model implemented, which family reviewed, what the reviewer rejected and why. It is also the enterprise "pen" pitch (DESIGN.md §23.1 — cross-vendor audit log, cost attribution, named reviewer) demonstrated as a product rather than claimed on a slide, using the same thin client that pitch would sell.
- **Stranger's scrutiny, institutionalized.** §23.1's sequencing rule says to use upstroke on real work "until it would survive a stranger's scrutiny" — this feature *is* that scrutiny, standing. Publishing the miss log is on-brand for a project whose records print `?` instead of `$0.00` and separate measured from assumed.

## Shape

Two stages, deliberately ordered:

1. **Replay theater (prototype shipped; generic v0.2-era path, no backend).** The repository already links a handcrafted public interactive replay and ledger from `README.md` and `docs/index.html`; that is the visual/proof-of-value prototype, not yet a generic run viewer. Live state and replay are the same fold, so the remaining precursor is safe generic event ingestion, an explicit public projection, and owner-approved automated publication of curated finished runs — including a failure run with its repair task, because that is the credibility moment. Zero uptime burden, ~90% of the value.
2. **Live board (v0.3, with the dashboard).** The same client pointed at a tail instead of a file. Arrives approximately for free once the dashboard exists.

## The three real work items hiding in "read-only"

1. **A public projection schema — not "the log with auth off."** Default-deny every free-text or content-bearing surface: diffs, plans, questions/answers, logs, paths, model prose, command output, and artifact bodies. The initial projection contains only typed low-risk allowlist fields such as event kind, stable public task key, state transition, coarse timestamps/durations, declared model family, verdict enum, and approved cost totals. A public repository is not publication authority for rejected or uncommitted diffs, unpublished plans, embargoed security work, operator paths, or accidentally introduced secrets. Content-bearing artifacts become eligible only after the exact material is merged or otherwise public **and** the owner explicitly approves that artifact for this projection. A deterministic regex scrub remains defense in depth after authorization, never the authorization rule itself.
2. **An untrusted-content browser contract.** Every projected string enters the DOM through text-only APIs such as `textContent`; the viewer never injects raw HTML or Markdown HTML. Links are generated only from a small scheme/host/path allowlist, never directly from event text. Projection and rendering reject or visibly escape control characters and bidirectional overrides. The static site ships a restrictive Content Security Policy with no inline script, remote script, plugin/object, form, framing, or arbitrary network destinations. Tests feed HTML, script URLs, ANSI/control bytes, and bidi text through the complete projection/render path.
3. **A deliberate call on capacity data.** Pool estimates, reset windows, and spend-down engaging are the operator's actual subscription state — and a public board captioned "watch me optimally drain my Claude Max window" advertises exactly the gray zone §20 says to re-verify with providers before public launch. The costs themselves are the killer content and should stay ($X/task with receipts is the number that sells); the *pool mechanics* may warrant coarsening. If this ships, the §20 ToS re-check moves earlier on the roadmap.

## Boundary

**Publish Phase 2, not Phase 1.** Execution runs, verdicts, merges, costs — yes. Interactive design sessions are half-formed thinking with the user in the loop; their durable output is already public in `decisions/`. Stream the orchestra, not the rehearsal.

## Non-goals

- No interaction channel of any kind (no comments, no answer input — answers only ever arrive via `upstroke answer` locally).
- No hosting obligation inside the engine; the viewer is a thin client and can be a static site.
- Not a monitoring product; it is a credibility and demo surface first.

## Open questions for council

1. Exact typed allowlist: which event types and low-risk fields per type enter the first projection?
2. Which content-bearing artifacts, if any, can an owner explicitly approve after merge/publication? Question/answer text remains denied by default.
3. How coarse should published capacity/pool data be, and does spend-down state appear?
4. Curated replays vs. publish-every-run: who curates, and by what rule?
5. Does the viewer share the dashboard codebase from day one, or does the replay theater ship first as a separate static page?
