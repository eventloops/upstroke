# Structured review-finding telemetry

**Status:** Draft
**Target:** v0.2 (telemetry foundation — land before more self-hosting history accumulates)
**Filed:** 2026-08-13
**Origin:** owner prompt, 2026-08-13; designed against the current source in a Fable 5 session (Anthropic seat).

---

## Summary

Reviews currently settle into pass/fail plus prose. The event log records *who* judged (`ReviewRecord`: adapter, model, CLI version, effort, pool, cost, outcome — `events.rs:576`) but not *what they found*; the verdict's `reasons`/`required_changes` survive only in the private review transcript and, on failure, in retry feedback. So telemetry can answer "how often did xhigh implementations pass review?" but not "did raising effort reduce findings?", "did findings shift from correctness to documentation?", or "which categories does each model catch?"

**Design verdict: extend the existing verdict contract — the fenced JSON object the reviewer already emits — with an optional `findings` array; carry it additively through `Verdict` → `ReviewRecord` → export schema 2. Record the contract and parse integrity on each settled review so mixed-version resumes remain honest. No new model calls, no prose parsing, no event-schema bump.** One invariant governs everything: **telemetry never changes a logically consistent verification outcome; a contradictory verdict still fails closed.**

## What exists today (measured against source)

- The reviewer prompt demands one fenced JSON block: `{"pass", "reasons", "required_changes", "needs_human"}` (`review.rs` prompt builder, ~`:693`). `parse_verdict` takes the **last** balanced JSON object, `pass` mandatory, lists defaulted (`review.rs:755`, `ir.rs:384`). One re-ask on unparseable; then the pass fails with a recorded reason.
- The raw reviewer answer is preserved as `<stem>[-suffix]-review.json` (and `-review-reask.json`) in the private reviews directory (`review.rs:512`) — **requirement 1 is already satisfied today**; nothing below touches it.
- Each pass settles into `events::ReviewRecord` at `engine.rs:3277`. The additive-field precedent is established three times on `AttemptRecord` (`pool`, `usage`, `reviews` — each `#[serde(default)]`, each explicitly *not* moving `SCHEMA_VERSION`), and the export decision records "bump the event schema for additive optional fields" as a **rejected alternative**.
- Export schema 1 (decided 2026-08-11) is normative: each `reviews` element has exactly `{pass, adapter_id, adapter_cli_version, model, effort, pool, cost_usd, outcome}`; CSV nests them as `reviews_json`; the export schema versions independently of the event schema.

## The change

### 1. Verdict contract v2

The prompt's schema block (and `REASK_PROMPT`'s copy) gains one member:

```json
{"pass": <...>, "reasons": [...], "required_changes": [...], "needs_human": <...>,
 "findings": [{"severity": "critical|high|medium|low",
                "blocking": true|false,
                "category": "correctness|security|reliability|concurrency|performance|architecture|scope|tests|documentation|maintainability|other",
                "summary": "<one line>",
                "path": "<repo-relative file, or null>"}]}
```

Prompt instructions added alongside:

- Report every blocking defect as `blocking: true`, set `pass: false`, and include a corresponding `required_change`. A pass still means the change introduces no defect under the review contract. Findings on a pass are explicitly **non-blocking observations** — useful cautions, trade-offs, or follow-up ideas — and must carry `blocking: false`. An empty array is an affirmative "nothing worth noting", distinct from omitting the key.
- Findings do not independently move a logically consistent verdict. `pass` keeps its existing bar, and severity alone is not a new gate. Whole-verdict validation does, however, settle the contradiction `pass: true` plus any `blocking: true` finding as a deterministic failed review without re-asking the model; telemetry cannot become a side channel for accepting a defect that the same JSON says is blocking.
- The anti-sycophancy stance and every existing instruction stand unchanged.

Cost: a few hundred output tokens per review. No additional invocation — the constraint that matters, since review measured at 44–77% of spend (DESIGN.md §23.2).

### 2. Types

```rust
/// One structured review observation. Severity/category remain advisory;
/// `blocking` participates only in whole-verdict consistency validation.
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub struct ReviewFinding {
    /// None when the reviewer's word was not one of the four levels;
    /// the raw string is preserved rather than coerced — an invented
    /// severity is worse than an honest absence.
    pub severity: Option<FindingSeverity>,   // critical | high | medium | low
    pub blocking: bool,                      // true requires pass=false + required_change
    pub category: FindingCategory,           // the 11 above; unknown → Other
    pub summary: String,                     // clamped to MAX_FINDING_SUMMARY_BYTES
    #[serde(default)]
    pub path: Option<String>,                // as claimed; not validated (the diff is the evidence)
    #[serde(default)]
    pub raw_severity: Option<String>,        // set only when normalization coerced
    #[serde(default)]
    pub raw_category: Option<String>,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
#[serde(rename_all = "snake_case")]
pub enum FindingsParseStatus {
    Absent,
    Complete,
    Partial,
    Invalid,
}
```

Normalization is case-insensitive exact match; anything else lands in `Other`/`None` **with the raw string preserved**, so taxonomy drift is measurable instead of laundered. No alias table — aliases breed silent drift.

Parsing (`verdict_from_json`) remains verdict-lenient but is no longer telemetry-silent. `Verdict` carries `Option<Vec<ReviewFinding>>`, a `FindingsParseStatus`, and an exact dropped-element count. **`Some([])` is reserved for an explicitly present empty source array.** An absent key produces `None / Absent / 0`; a wholly valid array produces `Some(values) / Complete / 0`; a mixed array retains its valid elements as `Some(values) / Partial / N`; a non-empty wholly invalid array produces `None / Invalid / N`; and a non-array value produces `None / Invalid / 0`. Non-object elements and objects without a `summary` or boolean `blocking` are invalid elements. This preserves useful partial telemetry without making malformed output look affirmative or fully compliant.

### 3. The invariant: telemetry never changes a consistent verification outcome

- `pass` remains the only policy outcome the ladder branches on (`ir.rs:380` stays true); the whole-verdict blocking/pass consistency rule validates one verdict rather than introducing a severity gate.
- Missing or malformed `findings` beside an otherwise consistent verdict: the verdict is accepted, telemetry is represented with the `Absent`/`Partial`/`Invalid` status above, and **no re-ask** is consumed. The existing re-ask stays reserved for a structurally unparseable verdict. A telemetry-motivated re-invocation would spend review dollars on analytics; a review that judged code must never be discarded over malformed metadata alone.
- A passing verdict may carry only `blocking: false` observations. `pass: true` plus `blocking: true` is a self-contradictory but structurally parsed verdict: settle it immediately as a failed review with a deterministic contradiction reason (and ordinary ladder feedback), preserving the raw transcript and consuming **no additional reviewer invocation**. Severity does not alter that rule.
- Non-compliance is itself telemetry: per-model `Absent`, `Partial`, and `Invalid` rates under the recorded per-review contract are measurable from the export.

### 4. Events — additive, no schema move

`ReviewRecord` gains:

```rust
#[serde(default)]
pub verdict_contract: Option<u32>,       // contract actually used for this verdict
#[serde(default)]
pub findings: Option<Vec<ReviewFinding>>,
#[serde(default)]
pub findings_parse_status: Option<FindingsParseStatus>,
#[serde(default)]
pub findings_dropped_count: Option<u32>,
#[serde(default)]
pub required_change_count: Option<u32>,   // measured at settlement from the parsed verdict
```

Populated at the `engine.rs:3277` settlement from each pass's parsed `Verdict`. Pre-existing logs fold to identical state (`None` for every additive field), the same justification written on `pool` and `usage`; `SCHEMA_VERSION` does not move, matching the export decision's rejected-alternative. `Unavailable` passes naturally carry `None` because no verdict contract was actually exercised. Finding summaries are one clamped line each — the full prose stays in the review transcript, which remains the authoritative evidence.

`required_change_count` is recorded rather than the strings because the strings already live in the transcript and (on failure) in retry feedback; duplicating prose into the log buys nothing the count does not.

### 5. Contract pinned in the run record

`run_started` records the intended `verdict_contract: 2` beside the review plan it already pins; absence on a legacy start means intended contract 1. A compatible binary resumes with that frozen prompt contract rather than whatever today's binary embeds. Crucially, **each `ReviewRecord` also records the contract actually used**. An older schema-2 binary may ignore a new run's field and append a legacy review; that record's absent per-review contract remains `null`/unknown rather than being falsely inferred as contract 2. A later compatible binary can therefore fold and export an honest mixed-contract history. The run-level field is intent; the per-review field is evidence. This additive design guarantees honest provenance across versions, not that an old binary can honor a contract it predates; requiring old binaries to refuse such a resume would need a schema transition/downgrade barrier and must be reconciled with schema 3's topology reservation. Neither absence nor an old binary's behavior is rewritten as compliance.

### 6. Export schema 2

- `schema_version: 2`.
- Each `reviews` element gains `verdict_contract`, `findings` (array as recorded, or `null` for absence — the `null`/`[]` distinction survives projection), `findings_parse_status`, `findings_dropped_count`, and `required_change_count`. Every field is the per-review recorded fact or `null`; export never promotes the run-level intended contract into a legacy pass.
- CSV changes nothing structurally: `reviews_json` already carries the nested objects, per schema 1's explicit rejection of flattening.
- No per-severity count columns: `finding_count`, severity buckets, and `finding_categories` are one-line consumer derivations from the array, and schema 1's provenance discipline (measured facts + deterministic derivations, nothing convenient in between) argues against materializing them. If council wants rectangular convenience columns for CSV analysis, that is an additive choice inside schema 2 — but the default is lean.
- Legacy runs export the new fields as `null` throughout and remain fully exportable (requirement 5). Mixed resumes expose each pass's actual/unknown contract and parse status. Export and event schemas continue to version independently.

## What this unlocks (requirement 8 mapping)

Effort vs. review quality (attempt `effort` × per-pass finding counts), reviewer/model effectiveness (per-pass `model`/`effort` × findings), first-pass quality (`attempt = 1` rows), severity distribution, retry/escalation effectiveness (finding trajectories across attempts of one task), task-kind × category correlations (`task_features.kind` × categories). All per-pass; nothing needs attempt-level flattening.

**Honesty caveat, carried from §23.2:** the same reviewer has passed and failed the identical line across two runs. Findings inherit that noise floor. The unit of interpretation is the aggregate distribution across many attempts, never a single-run delta — the export exists for calibration, not verdict-shopping.

## Deliberately not done

- No post-hoc parsing of reviewer prose (nondeterministic, fragile) and no second classifier invocation (a model call per attempt spent on telemetry, in the phase that already dominates cost).
- No severity/category gating and no retry for absent, partial, or invalid telemetry. The only outcome check is explicit `blocking: true` against `pass: true`; it prevents a contradictory verdict from being accepted without inferring policy from severity or category, and it never causes a reviewer re-ask.
- No backfill of old runs; absence stays honest.
- No cross-pass dedup: passes are independent by design (§11.3); merging their findings would require sharing what they must not share. Dedup is a consumer-side analysis step.
- No path validation against the diff. Recording the claim is measurement; judging it is review. (A deterministic warn-only cross-check against the candidate's changed paths is a cheap future add if claimed paths prove unreliable.)

## Tests required

Parse (`review.rs`):
1. Verdict with well-formed findings parses; severities/categories normalized; round-trips.
2. Explicit empty array → `Some([]) / Complete / 0`; absent key → `None / Absent / 0`, distinguished after serde round-trip.
3. Non-array, mixed-validity, and wholly invalid non-empty `findings` produce the exact `Invalid`/`Partial` status and dropped count above; no malformed non-empty input becomes `Some([])` and **no re-ask is consumed** when the verdict itself is consistent.
4. Unknown category → `Other` with `raw_category`; unknown severity → `None` with `raw_severity`; case-insensitivity.
5. Last-object rule unchanged when an earlier example block contains findings.
6. Summary clamping at the named constant.

Ladder/engine:
7. A pass with a non-blocking observation still passes; `pass: true` plus a blocking finding settles once as a failed review with deterministic feedback and no re-ask, while `pass: false` plus a blocking finding and corresponding required change settles normally.
8. Actual `verdict_contract`, findings, parse status, dropped count, and `required_change_count` are recorded per pass at settlement; `Unavailable` records `None` for verdict-derived fields.

Events/replay:
9. A pre-findings log line folds byte-identically to today's state (serde default); live fold and replay agree (the one-fold invariant).
10. Intended `verdict_contract` is recorded on `run_started`; a compatible resume honours it and records the actual contract per settled pass. A legacy/older-binary pass remains per-review `None` rather than being derived from the run, and a mixed-contract replay equals the live fold.

Export:
11. `schema_version` is 2; all new fields are present per pass; legacy runs export them as `null`; mixed resumes retain actual/unknown contracts and parse integrity; CSV `reviews_json` carries the same records; existing validation (negative cost, pairing) is unchanged.

## Open questions for council

1. Clamp size for `summary` (proposal: a named constant near the 8 KB feedback-tail conventions, ~400 bytes).
2. Should CSV get flat convenience count columns inside schema 2, or stay lean (proposal: lean)?
3. Should the prompt cap findings count (e.g., "at most 20, most severe first") to bound token growth on messy diffs?
4. Does `verdict_contract` live beside the review plan or inside it? (Cosmetic; either honours the record-not-re-derive rule.)

## Rejected alternatives

- **Parse findings out of reviewer prose.** Nondeterministic against the measured reviewer noise floor; a second parsing layer to maintain; the reviewer already ends with structured JSON — growing that contract is strictly smaller.
- **A separate classification pass over the transcript.** One more model invocation per attempt in the most expensive phase, to produce data the reviewer could have emitted for free.
- **Hard-require findings (re-ask or fail when absent).** Converts telemetry into a verification gate, violates the invariant, and spends review budget enforcing analytics compliance. Non-compliance is recorded and measured instead.
- **Record full `required_changes`/`reasons` strings in events.** Already preserved in the transcript and in failure feedback; the count answers the analytic question without duplicating prose.
- **Bump the event schema.** The additive `#[serde(default)]` pattern is established precedent on this exact struct family, and the export decision explicitly rejected bumping for additive optional fields. Export schema 2 is the honest, decided place for the contract change consumers see.
