# Structured review-finding telemetry

**Status:** Draft
**Target:** v0.2 (telemetry foundation — land before more self-hosting history accumulates)
**Filed:** 2026-08-13
**Origin:** owner prompt, 2026-08-13; designed against the current source in a Fable 5 session (Anthropic seat).

---

## Summary

Reviews currently settle into pass/fail plus prose. The event log records *who* judged (`ReviewRecord`: adapter, model, CLI version, effort, pool, cost, outcome — `events.rs:576`) but not *what they found*; the verdict's `reasons`/`required_changes` survive only in the private review transcript and, on failure, in retry feedback. So telemetry can answer "how often did xhigh implementations pass review?" but not "did raising effort reduce findings?", "did findings shift from correctness to documentation?", or "which categories does each model catch?"

**Design verdict: extend the existing verdict contract — the fenced JSON object the reviewer already emits — with an optional `findings` array; carry it additively through `Verdict` → `ReviewRecord` → export schema 2. No new model calls, no prose parsing, no event-schema bump.** One invariant governs everything: **telemetry must never change a verification outcome.**

## What exists today (measured against source)

- The reviewer prompt demands one fenced JSON block: `{"pass", "reasons", "required_changes", "needs_human"}` (`review.rs` prompt builder, ~`:693`). `parse_verdict` takes the **last** balanced JSON object, `pass` mandatory, lists defaulted (`review.rs:755`, `ir.rs:384`). One re-ask on unparseable; then the pass fails with a recorded reason.
- The raw reviewer answer is preserved as `<stem>[-suffix]-review.json` (and `-review-reask.json`) in the private reviews directory (`review.rs:512`) — **requirement 1 is already satisfied today**; nothing below touches it.
- Each pass settles into `events::ReviewRecord` at `engine.rs:3277`. The additive-field precedent is established three times on `AttemptRecord` (`pool`, `usage`, `reviews` — each `#[serde(default)]`, each explicitly *not* moving `SCHEMA_VERSION`), and the export decision records "bump the event schema for additive optional fields" as a **rejected alternative**.
- Export schema 1 (decided 2026-08-11) is normative: each `reviews` element has exactly `{pass, adapter_id, adapter_cli_version, model, effort, pool, cost_usd, outcome}`; CSV nests them as `reviews_json`; the export schema versions independently of the event schema.

## The change

### 1. Verdict contract v2

The prompt's schema block (and `REASK_PROMPT`'s copy) gains one member:

```json
{"pass": <...>, "reasons": [...], "required_changes": [...], "needs_human": <...>,
 "findings": [{"severity": "critical|high|medium|low",
               "category": "correctness|security|reliability|concurrency|performance|architecture|scope|tests|documentation|maintainability|other",
               "summary": "<one line>",
               "path": "<repo-relative file, or null>"}]}
```

Prompt instructions added alongside:

- Report **every defect noticed, including on a pass** — this is the load-bearing behavioural change. Today a passing review surfaces nothing structured, so "did effort reduce findings?" is unanswerable precisely where it matters. An empty array is an affirmative "nothing worth noting", distinct from omitting the key.
- Findings do not move the verdict. `pass` keeps its existing bar; a finding is an observation, a `required_change` is a demand. Every required change should have a corresponding finding; findings without required changes are legitimate on a pass.
- The anti-sycophancy stance and every existing instruction stand unchanged.

Cost: a few hundred output tokens per review. No additional invocation — the constraint that matters, since review measured at 44–77% of spend (DESIGN.md §23.2).

### 2. Types

```rust
/// One structured review observation. Advisory by construction: nothing in
/// the ladder branches on it (the invariant below).
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
pub struct ReviewFinding {
    /// None when the reviewer's word was not one of the four levels;
    /// the raw string is preserved rather than coerced — an invented
    /// severity is worse than an honest absence.
    pub severity: Option<FindingSeverity>,   // critical | high | medium | low
    pub category: FindingCategory,           // the 11 above; unknown → Other
    pub summary: String,                     // clamped to MAX_FINDING_SUMMARY_BYTES
    #[serde(default)]
    pub path: Option<String>,                // as claimed; not validated (the diff is the evidence)
    #[serde(default)]
    pub raw_severity: Option<String>,        // set only when normalization coerced
    #[serde(default)]
    pub raw_category: Option<String>,
}
```

Normalization is case-insensitive exact match; anything else lands in `Other`/`None` **with the raw string preserved**, so taxonomy drift is measurable instead of laundered. No alias table — aliases breed silent drift.

Parsing (`verdict_from_json`) is element-lenient: a non-object element or one without a `summary` is dropped; a `findings` value that is not an array reads as absent. `Option<Vec<ReviewFinding>>` on `Verdict`, `#[serde(default)]`: **`None` = the reviewer did not provide findings; `Some([])` = the reviewer affirmatively found nothing.** The distinction is the same house rule as "an absent record is not a record of no reviewers".

### 3. The invariant: telemetry never changes verification

- `pass` remains the only field the ladder branches on (`ir.rs:380` doc comment stays true).
- Missing or malformed `findings` beside a well-formed verdict: the verdict is accepted, findings read `None`, **no re-ask**. The re-ask stays reserved for an unparseable *verdict*. A telemetry-motivated re-invocation would spend review dollars on analytics; a review that judged code must never be discarded over its metadata.
- A passing verdict carrying critical-severity findings still passes. If that ever feels wrong, the fix is a verification-policy change through the ladder (§11.5's lens mechanism exists for exactly that) — explicitly out of scope here.
- Non-compliance is itself telemetry: the per-model rate of `None` findings under contract v2 is measurable from the export.

### 4. Events — additive, no schema move

`ReviewRecord` gains:

```rust
#[serde(default)]
pub findings: Option<Vec<ReviewFinding>>,
#[serde(default)]
pub required_change_count: Option<u32>,   // measured at settlement from the parsed verdict
```

Populated at the `engine.rs:3277` settlement from each pass's parsed `Verdict`. Pre-existing logs fold to identical state (`None`), the same justification written on `pool` and `usage`; `SCHEMA_VERSION` does not move, matching the export decision's rejected-alternative. `Unavailable` passes naturally carry `None`. Finding summaries are one clamped line each — the full prose stays in the review transcript, which remains the authoritative evidence.

`required_change_count` is recorded rather than the strings because the strings already live in the transcript and (on failure) in retry feedback; duplicating prose into the log buys nothing the count does not.

### 5. Contract pinned in the run record

`run_started` records `verdict_contract: 2` beside the review plan it already pins. Two reasons, both from the resume-gate-config decision's philosophy: a resume must issue the prompt shape the run started with rather than whatever today's binary embeds, and `findings: None` becomes interpretable — under contract 2 it is reviewer non-compliance; under contract 1 (or a legacy log without the field, derived as 1) it is history. Absence is never rewritten as compliance or refusal.

### 6. Export schema 2

- `schema_version: 2`.
- Each `reviews` element gains `findings` (array as recorded, or `null` for absence — the `null`/`[]` distinction survives projection) and `required_change_count` (integer or `null`).
- CSV changes nothing structurally: `reviews_json` already carries the nested objects, per schema 1's explicit rejection of flattening.
- No per-severity count columns: `finding_count`, severity buckets, and `finding_categories` are one-line consumer derivations from the array, and schema 1's provenance discipline (measured facts + deterministic derivations, nothing convenient in between) argues against materializing them. If council wants rectangular convenience columns for CSV analysis, that is an additive choice inside schema 2 — but the default is lean.
- Legacy runs export `findings: null` throughout and remain fully exportable (requirement 5). Export and event schemas continue to version independently.

## What this unlocks (requirement 8 mapping)

Effort vs. review quality (attempt `effort` × per-pass finding counts), reviewer/model effectiveness (per-pass `model`/`effort` × findings), first-pass quality (`attempt = 1` rows), severity distribution, retry/escalation effectiveness (finding trajectories across attempts of one task), task-kind × category correlations (`task_features.kind` × categories). All per-pass; nothing needs attempt-level flattening.

**Honesty caveat, carried from §23.2:** the same reviewer has passed and failed the identical line across two runs. Findings inherit that noise floor. The unit of interpretation is the aggregate distribution across many attempts, never a single-run delta — the export exists for calibration, not verdict-shopping.

## Deliberately not done

- No post-hoc parsing of reviewer prose (nondeterministic, fragile) and no second classifier invocation (a model call per attempt spent on telemetry, in the phase that already dominates cost).
- No severity gating, no findings-driven retry policy — verification semantics are untouched by construction.
- No backfill of old runs; absence stays honest.
- No cross-pass dedup: passes are independent by design (§11.3); merging their findings would require sharing what they must not share. Dedup is a consumer-side analysis step.
- No path validation against the diff. Recording the claim is measurement; judging it is review. (A deterministic warn-only cross-check against the candidate's changed paths is a cheap future add if claimed paths prove unreliable.)

## Tests required

Parse (`review.rs`):
1. Verdict with well-formed findings parses; severities/categories normalized; round-trips.
2. `Some([])` vs. absent-key → `None`, distinguished after serde round-trip.
3. Malformed `findings` (non-array; junk elements) beside a valid verdict → verdict accepted, findings `None`/partial, **no re-ask consumed**.
4. Unknown category → `Other` with `raw_category`; unknown severity → `None` with `raw_severity`; case-insensitivity.
5. Last-object rule unchanged when an earlier example block contains findings.
6. Summary clamping at the named constant.

Ladder/engine:
7. A passing verdict with critical findings still passes and emits no feedback (the invariant, asserted).
8. Findings and `required_change_count` recorded per pass at settlement; `Unavailable` pass records `None`.

Events/replay:
9. A pre-findings log line folds byte-identically to today's state (serde default); live fold and replay agree (the one-fold invariant).
10. `verdict_contract` recorded on `run_started`; resume honours the recorded contract; legacy logs derive contract 1 with a warning, and the resume records what it settled on.

Export:
11. `schema_version` is 2; new fields present per pass; legacy run exports `findings: null` and stays loudly valid; CSV `reviews_json` carries findings; existing validation (negative cost, pairing) unchanged.

## Open questions for council

1. Clamp size for `summary` (proposal: a named constant near the 8 KB feedback-tail conventions, ~400 bytes).
2. Should CSV get flat convenience count columns inside schema 2, or stay lean (proposal: lean)?
3. Should the prompt cap findings count (e.g., "at most 20, most severe first") to bound token growth on messy diffs?
4. Does `verdict_contract` live beside the review plan or inside it? (Cosmetic; either honours the record-not-re-derive rule.)

## Rejected alternatives

- **Parse findings out of reviewer prose.** Nondeterministic against the measured reviewer noise floor; a second parsing layer to maintain; the reviewer already ends with structured JSON — growing that contract is strictly smaller.
- **A separate classification pass over the transcript.** One more model invocation per attempt in the most expensive phase, to produce data the reviewer could have emitted for free.
- **Hard-require findings (re-ask or fail when absent).** Converts telemetry into a verification gate, violates the invariant, and spends review budget enforcing analytics compliance. Non-compliance is recorded and measured instead.
- **Record full `required_changes`/`reasons` strings in events.** Already preserved in the transcript and in failure feedback; the count answers the analytic question without duplicating prose.
- **Bump the event schema.** The additive `#[serde(default)]` pattern is established precedent on this exact struct family, and the export decision explicitly rejected bumping for additive optional fields. Export schema 2 is the honest, decided place for the contract change consumers see.
