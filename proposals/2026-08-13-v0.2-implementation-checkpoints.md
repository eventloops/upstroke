# Engine-owned implementation checkpoints and selective rewind

**Status:** Draft
**Target:** v0.2 (after streamed supervision and per-task worktrees; before broad parallel self-hosting)
**Filed:** 2026-08-13
**Origin:** owner prompt, 2026-08-13: if one implementation progresses `A → B → C → D` and D is a bad direction, restore C and refine it instead of discarding A–C.

---

## Summary

Tactus should preserve bounded, engine-owned checkpoints during one implementation generation. A long task may finish coherent increments A, B, and C before making a poor change D. When gates, review, the worker, or the operator identifies D as the wrong baseline, the next generation can restore C and continue from there.

Checkpoints are immutable private Git objects under engine-owned refs. They are **not accepted commits**, public Git tags, dependency-ready state, or review evidence. Only a final result that passes the ordinary complete gates and review may become a verified candidate, and only integration makes it authoritative. The sibling [commit-provenance proposal](2026-08-13-v0.2-tactus-commit-provenance.md) labels accepted authoritative commits as `Initial work → Fix N`; this proposal preserves the unapproved internal steps that may lead to one of them.

The key invariant is:

> Rewind changes where implementation resumes, never what verification must judge.

After restoring C, final gates and every reviewer still receive the complete task-base-to-final-result tree/diff. A checkpoint can save work; it cannot hide A–C from review or turn C into trusted code.

## What exists today

v0.1 keeps one cumulative dirty tree only for a same-rung retry that can resume the same agent session (`DESIGN.md` §14). Every escalation, deferral, budget stop, process error, crash resume, or non-resumable retry cleans back to the last authoritative commit. That rule is safe, but coarse:

- a same-session retry may repair D in place, yet has no stable C to return to;
- a reviewer outage can discard an otherwise strong implementation because no verdict settled it;
- a process crash cannot retain the worker session because the corresponding dirty tree is deliberately removed; and
- a fresh higher-rung worker often reimplements A–C before it can address D.

The three August self-hosting runs demonstrated the cost: multiple independently good implementations passed repository gates, then reviewer timeouts caused clean retries from the task base. Their transcripts survive, but their useful trees do not.

## Protocol

### 1. One generation may contain several worker segments

A task attempt/generation may invoke the same implementer session in bounded segments. At a natural coherent boundary the worker returns a structured terminal disposition:

```json
{
  "implementation_state": "checkpoint",
  "label": "parser and replay substrate",
  "summary": "registry operations and replay fold are complete; engine migration remains"
}
```

or:

```json
{"implementation_state": "complete"}
```

The process must return before a checkpoint is captured; Tactus never snapshots while an agent or tool subprocess may still be writing. If the adapter cannot provide this structured disposition, that binding remains single-segment rather than guessing boundaries from silence, elapsed time, or arbitrary tool events.

A checkpoint response is only a request. The coordinator validates scope, captures the tree, records it, and then may resume the same session with an acknowledgement and the next objective. The agent never runs Git, chooses refs, assigns checkpoint numbers, or declares a checkpoint trusted.

The frozen run policy bounds checkpoint count, cumulative worker wall time, reported spend, and retained bytes. Reaching a bound asks the worker to complete; it does not silently grant another attempt allowance every time the model checkpoints.

### 2. Checkpoint objects are private and immutable

Each checkpoint has a coordinator-issued identity `(run, task-key, generation, sequence)` and a private ref such as:

```text
refs/tactus/runs/<run-id>/tasks/<task-key>/generations/<generation>/checkpoints/<sequence>
```

The object is a synthetic commit whose parent is the previous checkpoint (or the frozen task base for sequence 0), allowing ordinary Git tree restoration and diff inspection. It carries `Tactus-Role: checkpoint` plus run/task/generation/sequence trailers. It is never placed on the run branch or protected target, and the eventual authoritative commit is created from the final verified tree against the authoritative parent—not by merging the checkpoint chain into public history.

Before Git writes new blobs, the coordinator enumerates the exact tracked/untracked checkpoint set and applies deterministic path, size, binary, credential-shape, and private-artifact exclusions. A denied or oversized snapshot is refused with feedback; writing a secret into an object and detecting it afterwards is too late. Configured checkpoint gates may then classify the snapshot:

- `raw`: structurally captured and safety-scanned, but no build claim;
- `gate_passed`: the frozen checkpoint-gate set passed against the exact tree.

Checkpoint gates run against a disposable materialization of that immutable tree. Their build products and other residue can neither change the checkpoint nor leak into the active implementation worktree. Neither class means reviewed. Automatic rewind prefers the latest `gate_passed` checkpoint; choosing `raw` requires an explicit worker recommendation accepted by policy or an operator choice.

### 3. Creation follows the existing event/ref transaction discipline

The coordinator is the sole event and ref writer. Checkpoint creation reuses the candidate protocol's crash-safe shape:

1. materialize the exact tree and synthetic commit without moving an authoritative ref;
2. append `checkpoint_prepared` with identity, parent/base, commit, tree, classification, label, safety result, gate evidence, expected old checkpoint ref, and frozen size counters;
3. compare-and-swap the private checkpoint ref;
4. append `checkpoint_created`.

On resume, expected-old means retry the same ref transition, expected-new means append the missing completion, and any third value means refuse as foreign mutation. An object without a prepared record is residue, never an adoptable checkpoint. Live fold and replay therefore expose exactly the same checkpoint inventory.

### 4. Rewind is an explicit recorded transition

A failed final state D does not automatically mean “latest checkpoint wins.” The ladder chooses one of:

- repair D in the same resumable session, preserving current behavior;
- restore a named checkpoint, normally the latest `gate_passed` C;
- start again from the authoritative task base; or
- ask the operator when the evidence cannot distinguish them safely.

`checkpoint_restored` records the selected checkpoint commit/tree, the discarded tree/diff digest, the failure that motivated the choice, and the new generation identity. Restore is a hard reset of the isolated task worktree plus exact untracked-file reconstruction from the checkpoint. The old worker session is not resumed: it believed D existed, so pairing it with C would violate the session/workspace identity rule. A fresh worker receives the original task, accumulated verification feedback, checkpoint label/summary, and an explicit statement that C is an unreviewed execution baseline.

The discarded D evidence remains in the private transcript/review artifacts and event digests. The mutable worktree is cleaned, but the record does not pretend D never happened.

### 5. Verification always returns to the task base

Checkpoint ancestry is an implementation optimization only. When the fresh worker refines C into E:

- capture and gates operate on the complete frozen task-base → E candidate;
- test-provenance checks still compare the authoritative base and E;
- reviewers see the complete diff and resulting repository state, not only C → E;
- path leases and blast-radius calculation use the complete changed-path set; and
- the authoritative commit/candidate records no checkpoint as its public parent.

This prevents a malicious or mistaken worker from placing a defect in A, checkpointing C, and asking review to judge only the small repair after C.

## Tags, refs, and visible history

The A/B/C checkpoints use private refs rather than public Git tags because they have not passed final review. Tactus may expose them through local commands:

```text
tactus checkpoint list <run-id> <task-id>
tactus checkpoint diff <checkpoint-id>
tactus checkpoint restore <run-id> <task-id> <checkpoint-id>
```

The restore command only answers/steers a parked or explicitly paused run while holding its coordinator lock; it is not an out-of-band `git reset` escape hatch.

Once a result is accepted, the commit-provenance proposal may publish annotated revision tags such as `Initial work`, `Fix 1`, and `Fix 2`. Thus both views remain honest:

```text
private implementation: A → B → C ──X D
                                  └──→ E

accepted history:       Initial work → Fix 1 → Fix 2
```

Repositories that deliberately want to archive raw checkpoints can export a private bundle/artifact under a separate retention policy. Publishing checkpoint refs as normal release/provenance tags is not the default.

## Retention and safety

- Checkpoint refs are local and excluded from ordinary push specifications.
- Terminal successful runs may delete raw checkpoints immediately and retain gate-passed checkpoints for a configurable short audit/recovery window; parked/failed runs retain them until resolved or explicitly pruned.
- Deleting refs makes objects eligible for Git garbage collection but is not secure erasure. A checkpoint that somehow contains a secret triggers the repository's credential-response procedure, not a claim that ref deletion erased it.
- Limits apply per task and run to checkpoint count, aggregate bytes, individual file size, and binary blobs. Generated/ignored/private run artifacts remain excluded.
- A checkpoint never satisfies a dependency, required status, reviewer verdict, release input, or “built by Tactus” accepted-commit metric.

## Tests required

1. A segmented fake worker produces A, B, C, then D; each checkpoint ref/tree is exact, private, ordered, and absent from the run branch.
2. The coordinator cannot checkpoint while the worker/tool process is live, and an adapter without structured checkpoint support never invents one.
3. Path/size/binary/private-artifact and credential checks run before object creation; a denied secret leaves no new reachable checkpoint object/ref.
4. Checkpoint count, cumulative time/spend, and byte limits cannot be reset by opening another segment in the same generation.
5. Kill tests at object/prepared/ref/completion boundaries produce exactly one replayed checkpoint or fail closed on foreign ref movement.
6. Restoring C discards D, starts a fresh worker session, records the discarded-state digest, and reconstructs tracked plus approved untracked files exactly.
7. After C → E, gates/review receive task-base → E, not C → E; a defect introduced before C remains visible and blocks acceptance.
8. Raw versus gate-passed classification is replay-stable; automatic selection never prefers raw over an eligible gate-passed checkpoint.
9. The final accepted commit has the authoritative parent/tree and contains no private checkpoint chain in mainline ancestry.
10. Successful, parked, failed, pruned, and crash-resumed runs apply the frozen retention policy without leaking checkpoint refs into normal pushes.
11. Windows, macOS, Linux, host, and container runners agree on checkpoint identity and restoration semantics.

## Open questions for council

1. Which bindings can reliably return a structured checkpoint disposition without a second bespoke tool protocol?
2. Should checkpoint gates default to the task's complete frozen gate list, a named lightweight subset, or raw-only plus safety scanning?
3. What are sensible default count/byte/retention limits? The self-hosting use case suggests 4–8 checkpoints per long frontier generation.
4. May policy automatically restore the latest gate-passed checkpoint after a regression, or must the worker/reviewer explicitly name it?
5. Is local Git object storage sufficient, or should large checkpoint payloads use content-addressed private archives while Git stores only trees within a size limit?

## Rejected alternatives

- **Always reset to the task base.** Safest simple rule, but repeatedly discards known-good A–C and caused substantial duplicated frontier work in real runs.
- **Keep only the dirty worktree.** Helps one warm retry but is neither crash-stable nor selectively rewindable, and cannot safely survive scheduler handoff.
- **Let the coding agent commit or tag checkpoints.** Violates engine-owned Git, permits identity/ref collisions, and turns an untrusted worker request into protocol state.
- **Publicly tag every intermediate state `Initial work` / `Fix N`.** Makes unreviewed or broken trees resemble accepted history and permanently distributes material that may contain defects or sensitive residue.
- **Review only the delta from the selected checkpoint.** Saves context by hiding earlier code from the judge; it is a direct verification bypass.
- **Resume the old session after rewinding D to C.** The session and filesystem would describe different worlds. Start fresh and provide the checkpoint summary plus recorded feedback.
