## Why (b) did not fire, and why that is not a reason to spend more

The two same-rung retries this run produced were both from paths that
*deliberately* start cold:

- `parse-basic` attempt 2 followed the kill. `run_resumed` discards every
  uncommitted path and clears `session`/`resume_next` on every task, so a
  resumed retry cannot reuse a session whose account of the tree no longer
  holds.
- `format-policy` attempt 2 followed the park. §14 never resumes out of a park,
  for the same reason: parking discards the working tree.

Both are the engine being right. Neither is (b)'s mechanism, which is a *gate
or review* failure feeding back into a resumed session on the same rung.

**The kill pre-empted it.** The kill landed on `parse-basic` attempt 1 — the
very attempt whose review failure produced (b) on 2026-08-10, and this plan's
likeliest trigger for it. One run cannot demonstrate both the kill test and (b)
on the same task. The absence is test design, not evidence about the mechanism.

What makes it safe to leave: the path is untouched by the change set under
test. The only feedback-related fix (§12 decisions, `7a55300`) gates on human
answers in the `question_answered` handler; `ladder_retry` feedback is written
`human: false` through code this change set never touched, and no adapter
source file was modified, so the live `--resume` plumbing is identical to what
demonstrated (b) on 2026-08-10.
`a_gate_failure_recovers_on_the_same_rung_via_session_resume` covers it and
passes.

**One more thing this run did not re-exercise:** `run_resumed` recorded
`"discarded": []`. The kill beat the agent's first edit, so the half-written
files a kill normally strands were not there to throw away. Unit-covered, and
demonstrated live on 2026-08-10 (`["M src/lib.rs", "A src/size.rs"]`).

## What the run verified about the review fixes

Each of these could only be seen against a live engine from a second process.

- **A task waiting on a working dependency reads as queued, not blocked.**
  Concurrent `status` mid-run:

  ```
    readme: running now — attempt 1 on small (claude-haiku-4-5)
    parse-basic: queued
    parse-edges: queued
    format-policy: queued
    changelog: queued
  run in progress: 0 task(s) committed so far on tactus/run-01KZR609074EQ24BZ9TTKRA4H1
  state: running now (another process holds this run)
  ```

  `parse-basic` depends on `readme`. Before `b48bd9d` that line read
  ``blocked by `readme` `` — whose documented meaning is that a dependency
  failed or parked. Every task with a dependency said it, for the whole first
  half of every run.

- **Ended-run propagation still means what it says.** Immediately after the
  kill, with the run genuinely over: ``parse-edges: blocked by `parse-basic` ``
  and ``format-policy: blocked by `parse-edges` ``. The fix narrowed `Blocked`
  without deleting it.

- **The run lock survives a `kill -9` and refuses a second engine.**
  `7542d45` replaced `flock` with `fcntl(F_SETLK)` because `flock` is inherited
  across `fork`. Against the live run, a second engine was refused —
  `another tactus process is already driving run 01KZR609074EQ24BZ9TTKRA4H1
  (lock held on …)` — and after the 3-process tree kill the OS released the
  lock, so `status` read `interrupted` rather than `running now`. That release
  is the property the whole lock design rests on.

- **`running` is the lock *and* the log.** Live: `state: running now`. Killed:
  `state: interrupted … Continue it with: tactus resume`. Never the wrong one.

- **§12's loop terminates, from the other channel.** The operator's typed
  answer reached the worker *and* the reviewer, which is the 2026-08-10 run's
  serious defect staying fixed: `format_size` in the delivered tree falls back
  to bare bytes for inexact multiples and returns `"0"` for zero, with a
  comment citing round-tripping, and the reviewer accepted it on the same rung.

  Note which §12 channel this was. 2026-08-10 demonstrated the **exit 2 →
  `tactus answer` → `tactus resume`** path. Here the resume ran under the
  config's default interaction mode rather than the original invocation's
  `--interaction never` — flags are per-invocation — so the engine stayed live
  waiting, and `tactus answer` printed *"that run is live; it will pick this up
  and un-park the task"*. That is the **live-pickup** path. Both of §12's
  variants have now been observed on a real run.

## The defect this run found

Recorded before it is fixed, as `acceptance/README.md` asks.

**A killed run's summary line says it completed.** `tactus status` immediately
after the kill:

```
  readme: committed 3c7401c7c1384f09be002eb436ba82009571bd5d — Document the size-parsing API [small ok] (39.8s, claude-haiku-4-5 $0.0731 + review claude-opus-5 $0.2559)
  parse-basic: skipped (run halted)
  parse-edges: blocked by `parse-basic`
  format-policy: blocked by `parse-edges`
  changelog: skipped (run halted)
run complete: 1 task(s) committed on tactus/run-01KZR609074EQ24BZ9TTKRA4H1
state: interrupted — this run stopped without finishing, with 1 attempt(s) cut off mid-flight. Continue it with:
    tactus resume 01KZR609074EQ24BZ9TTKRA4H1
```

Two adjacent lines contradicting each other about a run that was killed with
one task committed, one attempt cut off, two skipped and two blocked.

**Pre-existing**, from `85e4e72` (step 4) — `git log -S` on the line places it
there, and nothing in the review fixes touches it. `RunReport::outcome()`
returns `Complete` whenever nothing halted, no budget stopped it and nothing is
parked, which is exactly what a killed run replays into. **`RunReport` has no
notion of interruption at all**; only `RunStatus` does, via `interrupted_run()`.
So `status::render` prints the report's outcome block and then contradicts it
one line later.

It surfaces only through `status`. `report.json` is written by `finish()`,
which never runs on a hard kill, so the file itself never holds the
contradiction.

This is the third member of a set. `2e5ab10` fixed the *live* case — a working
run reported as halted. `7bf4e01` fixed the *finished-but-claimed* case — a
resume's lock window rendering a stopped run as in progress. This is the
*interrupted* case: a run that stopped without recording a finish still claims
an outcome. Fixed in the commit after this one.
